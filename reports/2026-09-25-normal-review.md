**RDMCP-NR-002 — Medium — expired transfers can be revived and temporary files persist.** Origin: introduced by implementation; location `src/index.ts:128-133,154-156,177-183`. Expiry only runs when a session is used or listed, with no timer/sweep; it queues cleanup asynchronously under the transfer lock. `transfer()` calls `session()`, then updates `item.touched` and returns the item before the queued expiry check executes. **RDMCP-NR-003 — Medium — file and content search can return incomplete results as final output.** Origin: introduced by implementation; location `src/index.ts:158-162,172-173`. Desktop Commander's `start_search` launches ripgrep asynchronously, and `get_more_search_results` can report `IN PROGRESS` and `More results available`. **RDMCP-NR-004 — Medium — process output and termination audit are incomplete.** Origin: introduced by implementation; location `src/index.ts:184-190`. `observe()` requests `read_process_output` with `offset:0,length:1000`. In Desktop Commander 0.2.51 those are line-pagination parameters: the response can contain `remaining` lines, and a completed process's `offset:0` always reads its first 1000 retained lines. The wrapper parses an exit marker, sets the logical process to `finished`, and thereafter returns cached output without retrieving the remainder. Thus output beyond the first page is inaccessible through `process_output`. `process_kill` sets `finished` without recording an observed exit code/result; neither natural completion nor kill emits the required `process.exit` audit event. The short marker test does not cover pagination or kill. Impact: users lose output and the audit trail misses the required termination result. Required action: page DC output to the requested/available end with a stable cursor, preserve completion state and exit code, record termination audit for both paths, and exercise >1000 lines and kill in live-DC tests.

**RDMCP-NR-005 — Medium — local OAuth accepts malformed PKCE and unvalidated authorization parameters.** Origin: introduced by implementation; location `src/index.ts:208-239`. `/authorize` accepts any nonempty `code_challenge` and ignores a requested `scope`; `/token` accepts any nonempty `code_verifier` and does not compare a supplied `redirect_uri` with the authorization request. The current live test uses `a-verifier`, a short low-entropy value, confirming this weak path is part of the accepted fixture. [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) defines 43–128 unreserved characters for verifier and challenge; [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html) requires the token redirect URI to equal the one in the authorization request and defines `invalid_scope`. Impact: the advertised PKCE S256 authorization-code contract and the verification plan's invalid-scope/redirect cases are not enforced. Required action: validate PKCE challenge/verifier syntax and length, require the registered exact redirect URI at the token exchange, reject unsupported scope at authorization, and add negative HTTP tests. This concerns the local password OAuth flow; Google OIDC and public-client policy remain in P4.

**RDMCP-NR-006 — Low — session list omits specified expiry and state.** Origin: introduced by implementation; location `src/index.ts:17,168-170`. Functional requirements say a session retains creation, last-use, expiry and state, and `session_list` returns expiry. The model stores only `created`/`touched`, and the list returns only `session_id`, `created_at` and `last_used_at`. Impact: clients cannot tell when a session will expire from the documented API. Required action: expose the effective expiry (and store/derive the required state) and test it across activity and expiration.

### Remaining required findings

**RDMCP-NR-003 — Medium — incomplete search pagination remains.** Origin: carried implementation finding, still present at `src/index.ts:243-259`. The loop reads `get_more_search_results` with `length:100`, parses a possible next offset, then breaks on `Status: COMPLETED` even when that response says `More results available`. For a completed 115-result search, the initial DC text contains at most ten results and page zero contains results 0–99; results 100–114 are never fetched. The 115-result fixture can pass because it asserts only a filename that may be among the initial ten and a metadata total of 115. The five-page/deadline bound can likewise return `IN PROGRESS` as a successful final result without a usable continuation. Impact: callers receive an incomplete answer. Required action: continue through all advertised pages until complete with no more results, and make a bounded incomplete search explicit rather than silently successful. Assert all 115 distinct results, especially indices 100–114, in the live fixture.

**RDMCP-NR-004 — Medium — unobserved process completion has no audit event.** Origin: carried implementation finding, still present at `src/index.ts:295-314`. The output paging and observed kill path are fixed, but the only `process.exit` audit call is inside `observe()`, which runs solely during `process_output`, `process_status`, or `process_kill`. A process started and allowed to finish without a later tool call never emits its required exit-result audit. The regression fixture explicitly polls until finished, so it cannot catch this. Impact: the audit trail loses natural completions whenever a client does not poll. Required action: independently observe owned process completion while the service is running, record the actual exit result once, and test a short process that finishes without follow-up process calls.

**RDMCP-NR-006 — Low — `session_list` includes inactive sessions.** Origin: carried implementation finding, still present at `src/index.ts:158-169,265-267`. The requirement says the list contains active sessions only. The new list filters solely by user after the sweep; expired and closed sessions remain in the map for up to another session TTL, so both appear in `session_list`. Impact: clients see ended sessions as available and must infer validity despite the advertised active-only list. Required action: filter by `state === "active"` and effective expiry, and assert absence after close and expiry in a live fixture.

**RDMCP-NR-007 — High — new regression test cannot run as written in Ubuntu CI.** Origin: introduced by the fix commit at `test/regressions.test.ts:165,175`; direct workflow effect in `.github/workflows/lint.yml` Ubuntu Node 22 `npm test` job. The test unconditionally starts `for /L %i in (1,1,1005) do @echo line-%i` and `ping -n 3 127.0.0.1 > nul`, which are Windows `cmd.exe` commands. Desktop Commander selects `/bin/sh` on Ubuntu; those commands cannot produce the required 1,005 lines or Windows ping behavior there. Windows Node 22 pass does not validate the Ubuntu job. Impact: the configured pull-request CI test gate fails on Ubuntu. Required action: make process fixture commands platform-specific while preserving the same output and kill assertions, then run the Ubuntu Node 22 job or an equivalent Linux Node 22 test on the fix HEAD.

**RDMCP-NR-008 — Medium — startup cleanup can delete unrelated files in allowed roots.** Origin: introduced by fix at `src/index.ts:141-143`. `removeOrphans` recursively visits every configured file root and deletes any regular file matching `/^\.__rdmcp_[A-Za-z0-9_-]+\.upload$/` without checking a persisted transfer record or ownership. An ordinary file named `.__rdmcp_notes.upload` matches and is removed at service startup. The restart fixture deliberately creates a matching file and labels it owned, but no source evidence distinguishes it from unrelated user data. Impact: starting the server can remove user files inside allowed roots.
