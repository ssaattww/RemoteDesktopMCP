## Findings (severity order)

### R24-05-D1 — High: pre-manifest CI gate rejects the expected initial manifest state

- Origin/location: R24-05 design, `doc/design/ci-test-runtime-reduction-design.md:71,73–79`, especially sequence item 2 at line 76; mirrored as a gating criterion in `tasks/tasks-status.md:47`.
- Description/evidence: the plan generates and measures the new exact-inventory duration manifest only in sequence item 3, after the first three required-CI runs. Yet item 2 says an unexpected `missing`, `stale`, or `fingerprint-mismatch` manifest status must be resolved before proceeding. The supplied R24-04 run already had `manifestStatus: missing`; the R24-05 candidate is explicitly supposed to create a fresh manifest only after measurements, and changing the workflow/shard definition changes a fingerprint input. Thus the pre-measurement 5-shard candidate is expected to use baseline fallback (`missing` if no manifest file exists, otherwise likely fingerprint mismatch), not `applied`. The plan gives no way to satisfy item 2 and then reach item 3 without either preexisting candidate-specific measurements (contradicting the sequence) or treating the expected fallback as an error.
- Impact: implementation/CI execution would be blocked at the first three-run gate or would encourage applying unmeasured/stale durations to bypass it. It also blurs which runs demonstrate 5-shard coverage versus which runs demonstrate optimized 5-shard performance.
- Required action: explicitly state that the first three 5-shard runs are coverage/CI-sequencing runs and that `missing`/`fingerprint-mismatch` baseline fallback is expected before candidate measurements. Require all five assignments to be valid and total, all test files to run once, and preserve the baseline status in evidence. Generate and review the fresh manifest only after those runs; after registering it, record the resulting exact source HEAD separately (manifest registration changes the repository tree/commit), verify that HEAD’s plan reports `applied` and uses five shards, and run the final three applied-manifest CI repetitions on that exact HEAD. Keep the measurement artifact’s source/head/inventory identity explicit across the pre-manifest and applied-manifest phases.

No other design-blocking findings. The items below were checked with no additional finding:

- **Hypothesis and quantitative limits:** The arithmetic is correct as an idealized reference: 673/5 = 134.6 seconds, approximately 135; versus the observed 260-second shard, that idealized allocation leaves about 125 seconds of possible headroom. The text expressly calls this a simple split of one 3-shard run, not a forecast; lists omitted setup, queue, per-file estimate error, in-file concurrency and startup costs; disclaims a speedup or 180-second claim; and keeps the 260-second one-run observation distinct from the 272-second three-run median baseline. This is a credible experiment hypothesis, not evidence that the outcome will meet the target.
- **Metrics and target distinction:** Applied-manifest success is judged by three runs’ median maximum Windows Test step ≤192 seconds (≥80 seconds below the R24-03 272-second baseline); full workflow median ≤180 seconds is a separate three-minute goal. R24-04’s single 260-second measurement is explicitly not substituted for the baseline median.
- **Sequence and overlap:** The plan separates pre-manifest CI runs, measurement workflow, manifest review/registration, applied-plan verification, and three applied-manifest CI runs. It explicitly prohibits overlapping measurement and required CI, and asks for exact-head records. Except for D1’s expected fallback-state contradiction, the sequence is actionable. The applied-manifest phase appropriately tests the actual optimized mode instead of treating baseline fallback as optimization evidence.
- **R24-02 boundary:** The design excludes PR #62’s fixture-initialization changes and does not attribute full test durations to initialization. It identifies DR002/NR009 as that PR’s affected areas, then points out NR008 and the Commander stderr test as analogous potential costs for separate future work. This is accurate and keeps the 5-shard experiment scoped.
- **Test coverage/acceptance:** The design calls for no lost/duplicated test files in the five assignments, preserves Ubuntu full-suite execution, and requires Windows all-file coverage. Tracking retains both OS gates. The ≤192-second Windows shard target and ≤180-second full-workflow target are separately stated; failure leaves Issue #24 open.
