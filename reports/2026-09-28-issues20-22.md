## Windows CI の失敗原因と時間短縮

`8f8ed5b` と `c2239b4` の Windows CI は、同じ IFR-002 試験で失敗した。
失敗箇所は `unstable.initialize()` 全体へ課していた3.5秒未満の検証である。
ここには再試行前のディレクトリ・ACL準備、状態読込、Desktop Commander 起動も含まれる。
再試行自体の契約は約2秒・最大20回であり、初期化全体の時間とは異なる。
使用者の方針に従い、実行速度のアサーションはローカルの通常試験に残し、CI では実行しない。
修正では実際の pin-link 試行回数が最大20回以内であることを検証する。
サービスが準備完了にならないこと・失敗することの既存検証を維持し、対象試験は1回実行して成功した。
CI では各段階の個別所要時間を記録していなかったため、ACLと起動の内訳までは未計測。
プロセス停止試験の10秒未満という速度判定もローカル限定とし、停止結果と監査の検証は両方で維持する。
認証の受信期限・有効期限など機能仕様の時間検証は速度試験とは区別して維持する。
IFR-002 のローカル実行は速度サブテストを含め成功（約22.7秒）。
`CI=true` の実行は速度サブテストだけが SKIP となり、機能検証は成功した（約23.5秒）。

CI の Windows テスト工程は約700秒で、Ubuntuより長かった。
全試験を維持して Windows を3 shardへ分割し、同じ PR の古い実行を自動停止する。
短縮幅は変更後の CI で確認する。

`c022f28` の CI（`36428945602`）は Ubuntu と Windows 全3 shard が成功。
Windows 各ジョブは約6分45秒・2分43秒・5分45秒で、全体待ち時間は約6分45秒だった。
単一ジョブ時の約12〜14分からほぼ半減した。全機能テストを残し、速度サブテストだけを CI でスキップした。

`0e84bbf` の旧 Windows CI では、追加で IFR-004 の終了監査と出力取得、CLI の拒否試験が失敗した。
CLI は3秒の子プロセス待ちがタイムアウトし、IFR-004 は約2秒の観測窓内に監査永続化が完了していなかった。
Windows の監査・非公開ファイル確認は PowerShell による ACL 検証を伴う。
出力・終了監査を永続化してから終了状態を公開する順序は正しく、キューはサービスごとである。
製品の保護や監査順序を変えず、試験の機能完了待ちに余裕を持たせる。
これは速度の合否判定とは分離した、試験の停止防止用タイムアウトである。
修正後の対象試験は CLI 1件と IFR-004 2件が成功し、GPT-6 Sol high の差分レビューも通過した。
