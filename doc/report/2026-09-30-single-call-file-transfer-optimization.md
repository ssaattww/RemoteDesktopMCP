# 小容量ファイル転送の単発化とチャンクサイズ調整レポート

## 目的

ファイル転送の体感待ち時間を、実運用の転送サイズと監査ログに基づいて削減する。
特に、通常の小容量ファイルで複数回のMCPツール呼び出しを行わず、1回の呼び出しで転送を完了できるようにする。

## 実運用データ

監査ログ `transfer.begin` のサイズ情報24件を集計した。

| 指標 | 値 |
| --- | ---: |
| 件数 | 24 |
| 最小 | 0バイト |
| 中央値 | 5,085バイト |
| 75パーセンタイル | 8,812バイト |
| 90パーセンタイル | 10,770バイト |
| 95パーセンタイル | 11,897バイト |
| 最大 | 16,938バイト |
| 128 KiB以下 | 24 / 24 |
| 512 KiB以下 | 24 / 24 |

方向別では、アップロード23件の平均が6,082バイト、最大が16,938バイト、
ダウンロード1件が3,852バイトだった。

既定128 KiBの時点で実績24件はすべて1チャンクに収まっていた。
したがって、体感遅延の主因はチャンク内の転送速度ではなく、
アップロードの `begin → chunk → commit`、ダウンロードの `begin → chunk`
という複数のMCPツール呼び出しに分かれていたことと判断した。

過去の監査ログでは、転送ツールのサーバー内部処理時間はおおむね0.5～0.9秒だった一方、
次の独立したツール呼び出しまで約8～66秒空いた例がある。
そのため、通常サイズではMCP往復回数の削減を優先した。

## 採用した仕様

- 既定チャンクサイズを128 KiBから512 KiBへ変更した。
- 512 KiBは既存設定で許容していた最大値である。
- 512 KiBをbase64化した文字数は699,052文字であり、ツール入力上限700,000文字以内に収まる。
- MCPのJSON受信上限1,048,576バイトにも、通常のメタデータを含めて収められる範囲とした。
- ダウンロードは `file_transfer_download_begin` に `inline=true` を指定し、
  ファイル全体が1チャンク以内なら同じ呼び出しでbase64本体を返して完了する。
- アップロードは `file_transfer_upload_begin` にbase64本体 `data` を同梱し、
  1チャンク以内なら同じ呼び出しでサイズ・SHA-256を検証し、原子的な確定まで完了する。
- 1チャンクを超える場合は従来の分割転送を維持する。
- 既存クライアントとの互換性を保つため、単発経路は明示指定時だけ使用する。
  従来どおり `begin → chunk → commit` を使用する呼び出しは引き続き有効である。

実績24件と同じサイズ分布で単発経路を使用した場合、
基本転送経路のMCP呼び出し数は23件のアップロードで69回から23回へ、
1件のダウンロードで2回から1回へ減る。
合計では71回から24回となり、47回の往復を削減できる。

## 完全性と安全性

単発アップロードと従来のcommitで処理差が生じないよう、
既存の確定処理を共通の完了処理へまとめた。

単発経路でも次を維持する。

- 宣言サイズと実データサイズの一致確認
- SHA-256一致確認
- 一時ファイルの同一性確認
- 許可ルートの再確認
- `overwrite=false` 時の原子的な既存ファイル保護
- 完了監査ログ
- セッション所有権
- Emergency Stopの既存境界
- ダウンロード時の不変snapshot

## 1 MiB / 5 MiB / 25 MiB 性能実測

2026-10-01に `npm run benchmark:transfer` を実行し、512 KiBチャンクでupload/downloadを測定した。
測定区間は localhost の MCP Streamable HTTP で、最初の転送ツール呼び出し開始から最後の転送ツール応答受信までとした。
fixture準備、元ファイル作成、転送完了後のSHA-256検証はend-to-end時間から除外した。
server処理時間は、測定区間中の転送ツールに対応する `operation.succeeded.durationMs` の合計である。
tool call数は `file_transfer_*` の実呼び出し回数で、同じ区間の成功監査件数と一致することを測定スクリプトで確認した。

| 方向 | サイズ | tool call数 | server処理時間 | end-to-end時間 |
| --- | ---: | ---: | ---: | ---: |
| download | 1 MiB | 3 | 3,918 ms | 5,125 ms |
| upload | 1 MiB | 4 | 3,448 ms | 4,804 ms |
| download | 5 MiB | 11 | 9,224 ms | 13,268 ms |
| upload | 5 MiB | 12 | 8,893 ms | 13,035 ms |
| download | 25 MiB | 51 | 37,801 ms | 56,390 ms |
| upload | 25 MiB | 52 | 37,629 ms | 56,745 ms |

旧既定128 KiBで同じサイズを順次チャンク転送した場合の呼び出し回数は、仕様から計算するとdownloadが9 / 41 / 201回、uploadが10 / 42 / 202回となる。
今回の512 KiBではdownloadが3 / 11 / 51回、uploadが4 / 12 / 52回となり、呼び出し回数はdownloadで66.7% / 73.2% / 74.6%、uploadで60.0% / 71.4% / 74.3%減少する。
旧128 KiBの時間値は今回再計測していないため、時間短縮率としては扱わない。

今回の実測はlocalhost MCP HTTP区間であり、ChatGPT connector/Tailscaleを含む実運用経路のend-to-end時間ではない。
現在稼働中のサービスには本PRの512 KiB既定値と単発転送実装が未反映であるため、実運用経路の性能確認はサービス更新後の再計測事項として残す。
その再計測までは、実運用経路での待ち時間改善を完了扱いにしない。
