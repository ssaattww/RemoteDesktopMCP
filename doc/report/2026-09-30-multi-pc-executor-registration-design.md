## 洗い出した設計不備と対応

### セッションと実行ノードの所有関係

旧設計は1つのセッションにノードごとの作業ディレクトリを持たせ、同じセッションで複数 PC を切り替える案だった。

一方、既存要件ではプロセスの状態確認、出力取得、停止は起動時と同じ有効な `session_id` だけに許可している。
同じセッションの実行先を後から切り替えられると、起動元ノードと操作先ノードの境界が不明確になる。

対応:

- 1つの `session_id` を1台の `node_id` へ固定した。
- 作業ディレクトリもその対象ノード上の1個へ固定した。
- 別ノードまたは別作業ディレクトリを使う場合は新しいセッションを作成する。
- 廃止対象だった `session_set_working_directory` を公開操作から除いた。
- セッション固定先と操作対象が異なる場合は `SESSION_NODE_MISMATCH` で拒否する。

### セッション開始前のノード発見

複数 PC 構成では利用者が `session_open` の前に対象 `node_id` を知る必要があるが、旧案では `node_list` とセッション依存関係が明確でなかった。

対応:

- `node_list` は認証済み利用者がセッション開始前に呼び出せる読み取り操作とした。
- 互換目的で `session_id` を受け付ける場合も、一覧の絞り込みには使わない。
- 実行ノードを兼任する統括ノードと登録済み遠隔実行ノードを合計し、2台以上なら `session_open` でも `node_id` を必須とする。

### 再接続候補による既存接続の破壊

同じ `node_id` の新しい接続が相互認証に成功しただけで旧接続を置き換えると、利用者状態同期失敗や候補接続の故障によって正常な旧接続を失う。

対応:

- ノードごとに操作可能な `active` 接続1本と、置換候補の `synchronizing` 接続1本を持つ。
- 候補は `ready` と最新の使用者状態同期まで成功した場合だけ `active` へ昇格する。
- 候補の同期失敗時は候補だけを閉じ、既存 `active` を維持する。
- 候補昇格前には旧実行ノード世代の転送・プロセス対応を失効させない。

### TCP 再接続と実行ノード再起動の区別

旧設計では接続世代だけでは、単なる TCP 再接続と RemoteDesktopMCP 実行ノードプロセス自体の再起動を安全に区別できなかった。

対応:

- 実行ノードプロセスの起動ごとに `executor_generation` を生成する。
- 統括ノードとの TCP 再接続だけでは `executor_generation` を維持する。
- 実行ノードプロセス再起動では新しい `executor_generation` を使う。
- Desktop Commander の接続世代は `desktop_commander_generation` として別管理する。
- 実行ノード世代が変わった場合、旧世代の転送・プロセス資源を新しい世代へ付け替えない。

### 使用者状態の完全同期

停止要求だけを伝える方式では、停止後の再開や、切断中ノードの再接続時に現在状態を一意に再構成できない。

対応:

- 統括ノードを使用者状態の正とした。
- `principal_id`、`stopped`、`stop_generation`、`stop_id` を `user_state` で同期する。
- `user_state_ack` を受けるまで新しい接続候補を操作可能にしない。
- 停止と再開のどちらも全 `active` 接続と `synchronizing` 候補へ反映する。
- 未同期、古い停止世代、停止中の要求を実行ノード側で拒否する。

### 遠隔操作の許可境界

統括ノードから任意の Desktop Commander ツール名や PID を渡せる設計は、公開 MCP の制限を遠隔ノードで迂回する余地を作る。

対応:

- ノード間 `request` で送信できる内部操作名を固定一覧へ限定した。
- `session_validate_working_directory` は遠隔作業ディレクトリ確認専用の内部操作とした。
- 任意の Desktop Commander ツール名を遠隔要求に含めない。
- 統括ノードは遠隔 PID を保存・送信しない。

### 転送・プロセス資源の識別

公開IDをそのまま遠隔ノード内の資源識別子にすると、実行ノード再起動や PID 再利用時に別資源へ誤対応する余地がある。

対応:

- 公開 `transfer_id` と実行ノード内 `remote_transfer_id` を分離した。
- 公開論理プロセスIDと実行ノード内 `remote_process_id` を分離した。
- 公開IDの対応には `node_id` と `executor_generation` を保持する。
- プロセス資源はさらに `desktop_commander_generation` と PID の所有対応を実行ノード側で確認する。
- 同じ PID が再利用された場合は古い `remote_process_id` を無効化してから新しい所有者へ切り替える。
- 世代が一致しないIDから Desktop Commander へ PID を渡さない。

### 遠隔作業ディレクトリの検証

統括ノード側だけでは遠隔 PC 上の絶対パスの存在と実体を確認できない。

対応:

- `session_open` 時に対象遠隔ノード上で絶対パスを正規化し、存在するディレクトリだけを受け付ける。
- `process_start` の直前にも対象ノード上で存在を再確認する。
- 検証不能な切断中ノードではセッションを作成しない。

### 統括・実行兼任構成の設定

統括ノード自身が実行ノードを兼任する場合に、自分自身への上流接続設定を要求する解釈が残っていた。

対応:

- `role=both` は自身への統括ノード接続先と事前共有鍵を要求しない。
- 遠隔実行ノード登録は統括役割を持つノードの `executors[]` に限定する。
- 実行ノード専用構成だけが統括ノード接続情報を必須とする。

### ローカル兼任ノードの一覧状態

統括ノード自身が実行ノードを兼任する場合はノード間 TCP 接続を持たないため、遠隔ノードと同じ基準で `connected` を判定できない。

対応:

- ローカル実行経路の初期化に成功している間は `connected=true` とする。
- Desktop Commander の利用可否は `operations` とファイルルートへ反映する。
- 遠隔 TCP 接続がないことだけを理由にローカル兼任ノードを切断扱いにしない。
- `last_seen_at` はローカル能力を最後に確認した時刻とする。

### 認証済みフレームの改ざん検証

認証済みフレームでは本文だけでなく、処理の意味を変える `type` と `request_id` も完全性確認の対象である必要がある。

対応:

- HMAC 入力へ `type` と `request_id` を含める契約を維持した。
- 受け入れ条件へ `type` と `request_id` の改ざん試験を明記した。
- 未定義の `type` と `request_id` の組合せも拒否する。
