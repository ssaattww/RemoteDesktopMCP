# 課題43 使用者画面認証状態の設計

## 状態と範囲

本書は設計草案であり、製品コードや実稼働中の認証設定を変更しない。60分の無操作期限と8時間の最長期限案は未承認であり、承認前の実装・展開を禁止する。認証終了原因の整理と、利用者の操作だけで認証状態を延長する契約を定める。

対象は `/user` と `/api` の使用者画面認証である。OAuthによるMCP接続認証、`session_open` の操作セッション、実行プロセスの寿命は対象外とする。

## 原因の切り分け

コード上で第一候補となるのは、ログインから3,600秒後に到来する固定期限である。`src/user-console.ts` の `newLogin` は `Date.now() + 3600_000` で記録を作り、パスワード認証とGoogle認証後の戻り処理は `Max-Age=3600` の `rdmcp_user` 値を発行する。`/user` で値を再発行する場合も、既存の `login.expires` までの残り時間を設定するだけで、期限を先へ動かさない。継続利用中もログインから約1時間で値とサーバー側記録がともに期限切れとなる。

期限切れ後、`/api` は401を返し、`/user` は `/user/login` へ案内する。ログ通知の長期HTTP接続は `auth-expired` を通知する。ブラウザは初回に状態を一度取得した後、通知接続を維持する。定期生存通知は接続状態を表示するだけで認証要求を発行せず、ログイン値も更新しない。このため、通知を受けながら画面を開いていても期限は延びない。

ログイン記録は `mountUserConsole` 内のプロセス内 `Map` に保存される。プロセス再起動後は過去の値に対応する記録がなく、再ログインになる。ただし、今回の実際の認証終了が再起動で起きたという運用上の証拠は確認していない。

| 候補 | コード上の判定材料 | 現時点で言えること |
| --- | --- | --- |
| 固定1時間期限 | 値と `Login.expires` が3,600秒。認証済み要求で期限を延ばさない | 発生間隔が約1時間なら最有力。コードで因果を説明できる |
| 無操作期限 | 現行 `Login` に最終利用時刻や独立した無操作期限がない | 現行実装の原因ではない。提案では固定期限と分離する |
| 更新処理 | 使用者画面認証に期限更新処理がない | `/user` の再発行は残り時間を再掲しているだけ |
| 通知接続の再接続 | `/api/events` の再接続も通常の認証を通る。定期生存通知は期限を延ばさない | 接続断後に期限切れなら再認証が必要 |
| 認証プロセス再起動 | ログイン記録をプロセス内 `Map` のみで保持 | 再起動で全画面認証が失効する。永続化はない |
| 明示終了・認可撤回 | `/user/logout` は検査後に記録を削除。Google本人確認情報の許可を再確認 | 期待された境界として維持する |

課題 #22と変更 #23はログ本文を分離したHTTP通知の設計・実装であり、認証期限を扱わない。変更 #35はMCP接続用資格情報の同時更新競合を扱い、`rdmcp_user` の期限を変えない。課題 #39 と変更 #38 は端末から読む画面の設計であり、専用資格情報を増やさない方針である。課題 #46 の自動更新、課題 #47 の使用量定期取得もログイン状態の操作ではないため、無操作期限を延長してはならない。

`src/index.ts` の `SESSION_TTL` は操作セッション用の24時間無操作期限で、操作ごとに更新される。画面認証とは別の状態であり、期限を混同しない。

## 認証期限の契約案

プロセス内の不透明な認証記録を維持し、新しい資格情報の保存、OAuth権限範囲、外部依存を導入しない。認証期限を延ばすのは、画面上の利用者入力に対応する専用要求と、成功した明示的な状態変更だけとする。読取要求や失敗した操作を活動とみなさない。

- 未承認案は、無操作60分で失効、ログイン成立から8時間を最長期限とする。最長期限は更新操作でも動かさない。8時間案が承認されない場合は、許容される値が決まるまで現行値を維持し、実装しない。
- 認証記録に `createdAt`、`lastUserActivityAt`、`idleExpiresAt`、`absoluteExpiresAt` を保持する。両期限より現在時刻が前の場合だけ受理する。記録数の上限2,000件は維持する。
- `/user` の閲覧、`/api` の読み取り、課題 #46 の自動更新、課題 #47 の使用量取得、通知接続の開始・再接続・定期生存通知は背景通信であり、`lastUserActivityAt` と期限を更新しない。
- ブラウザは実入力の時刻を記録する。表示中であり、直近15分以内に `event.isTrusted` の入力があり、前回送信から15分以上経過した場合だけ `POST /api/session/refresh` を送る。直近の入力がなくなった時点で送信を止め、非表示や通信断の間も送らない。サーバーはこの専用要求だけを期限更新の候補として扱う。
- `/user/emergency-stop` と `/user/resume` は、認証・発信元・本人用トークンの検証後、状態変更が成功した場合だけ活動時刻を更新する。失敗応答、拒否、`/user/logout` は更新しない。認証終了は記録を直ちに失効させる。
- 延長前に認証状態、要求元、画面に埋め込まれた本人用トークンを検証する。認証切れ、要求元不一致、トークン不一致、認可拒否、所有者確認失敗、状態変更の失敗など、拒否・失敗した要求では記録や期限を一切更新しない。検証成功後のみ `lastUserActivityAt = now` とし、`idleExpiresAt = min(now + 60分, absoluteExpiresAt)` とする。
- 専用要求の送信間隔もサーバー側で制限する。並行・重複要求は一つの利用操作として扱い、期限更新を過剰に積み重ねない。専用要求の応答は `Cache-Control: no-store` とし、ログイン値や資格情報を本文に含めない。
- ブラウザに保存する期限は無操作期限と最長期限の残り時間の小さい方とする。サーバー側の期限判定を最終権威とし、保存値の有効期間がどちらかの期限を越えないようにする。
- 既存の保存先 `/`、`HttpOnly`、`SameSite=Lax`、HTTPS時の `Secure`、旧 `/user` 保存値の削除、画面読み込み制限、応答保存禁止を維持する。値の形式や認証主体の範囲を変えない。

8時間案は現行の絶対期限1時間を延ばすため、漏えいした認証値が使える最長時間を増やす。属性や所有者分離を保っても時間上の露出は増す。この上限はユーザー承認待ちであり、承認が得られるまで実装・稼働設定への適用を行わない。

## 操作・失効の境界

| 状態 | 判定と応答 |
| --- | --- |
| 未ログイン状態と認識できない値 | `/api` は既存の一律401、`/user` はログイン画面を案内する。未知値だけで再起動や改ざんを断定しない |
| 無操作期限 | 最終の受理済み利用者入力から60分後に失効する。期限到達後の更新要求は拒否し、期限を動かさない |
| 最長期限 | 未承認案ではログインから8時間で失効する。利用中でも越えられず、承認までは現行設定を維持する |
| 背景通信 | 読み取り、自動更新、使用量取得、通知接続の再接続や定期生存通知は期限を延長しない |
| 許可撤回 | 現行のGoogle本人確認情報の許可確認を維持し、拒否された記録は利用不可にする。拒否要求で期限を更新しない |
| 明示的認証終了 | 発信元と本人用トークンを検証して記録を削除し、`/` と旧 `/user` 保存値を期限切れにする。古い値の再利用を認めない |
| 要求拒否 | 認証、発信元、本人用トークン、認可、所有者確認のどれかに失敗した要求は期限を延長しない |
| プロセス再起動 | プロセス内記録が消えるため過去の認証は失効する。再認証を案内し、復元しない |
| 通知接続 | 接続や再接続だけでは延長しない。期限到達時は `auth-expired` を通知して閉じ、次の要求は通常の認証を通す |

再起動後に認証状態を復元する案は採らない。導入には保存先の保護、複数プロセスでの一貫した失効、鍵の保護と更新を含む別設計および追加承認が必要になる。

## 安全な診断

コードだけで本番の個別認証終了原因を断定しない。利用可能な匿名化した統計と記録があれば、時刻と件数を照合する。認証値、値の要約値、認可ヘッダー、パスワード、Google資格情報、メールアドレス、ユーザー主体、IPアドレスを読み出したり記録したりしない。

必要な場合だけ、低頻度で固定の分類と件数を記録する。候補は未提示、無操作期限、最長期限、許可撤回、明示終了、プロセス開始、要求元検証失敗である。外部応答へ失敗理由を追加せず、既存の一律401/403を維持する。再起動後の未知値は「対応する記録がない」とだけ数え、直前に有効な記録があったとは推定しない。既存の安全な匿名化ログで足りれば新しいログを追加しない。

## 実装前の試験計画

時刻は `mountUserConsole` に試験用 `now()` 関数を注入して進める。共通の `Date.now` の差し替え、実認証設定変更、稼働サービスの再起動、実ユーザーの認証終了操作は行わない。

1. パスワード認証とGoogle認証後の戻り処理が同じ期限・保存属性を設定すること。
2. 59分時点では有効であり、60分到達後は `/api` が401、`/user` が再認証案内となること。
3. `/user` 閲覧、読み取りAPI、課題 #46/#47 の定期通信、通知接続の開始・再接続・生存通知を行っても無操作期限が変わらないこと。
4. 表示中の信頼できる入力後に限り、15分以上間隔を空けた専用更新要求が受理され、無操作期限を更新すること。偽造入力、非表示画面、無操作時には送られないこと。
5. 認証切れ、要求元不一致、本人用トークン不一致、認可拒否、所有者確認失敗、状態変更失敗では記録・期限が変わらないこと。認証と検査の前に期限更新処理へ到達しないこと。
6. 保存値の期限が無操作・最長期限の残り時間の小さい方を超えず、最長期限直後は更新要求も拒否されること。8時間値は承認まで実装設定に採用しないこと。
7. 定期生存通知では延長せず、両期限到達時に `auth-expired` を送り接続を閉じること。再接続後も通常認証で拒否されること。
8. 明示終了後は以前の値で画面、API、通知、専用更新を再利用できないこと。別利用者の値から他者のデータを取得できないこと。
9. 許可撤回後のアクセスを拒否し、拒否要求で期限を延長しないこと。
10. 別の `mountUserConsole` を作る単体試験で再起動後のプロセス内記録消失を表現し、以前の値を拒否すること。実プロセス再起動は行わない。
11. 診断出力を捕捉し、固定の分類のみで、認証値、主体、メールアドレス、IPアドレスが含まれないことを確認すること。

## 親による判断事項

- 絶対期限を現行1時間から8時間へ延ばす案はユーザー承認待ちである。承認または別の上限が定まるまで実装しない。
- 利用者入力だけで期限を更新する専用要求と15分の最小間隔を確認する。
- 読み取り、自動更新、使用量取得、通知接続の再接続は延長しない契約を確認する。
- 再起動時の失効維持と、永続化を本件範囲外とする方針を確認する。
