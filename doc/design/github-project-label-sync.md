# 課題表の優先度・状態と課題分類の連携

## 目的と対象

個人用の `Project #4` と `ssaattww/RemoteDesktopMCP` の課題を、`Priority` と `Status` について双方向同期する。対象は `Project #4` に登録された、このリポジトリの課題だけとする。`pull_request`、別の課題表、別リポジトリの項目は変更しない。

同期は MCP サーバーの実行時機能と分け、専用の `GitHub Actions` で行う。依存は追加せず、`GitHub GraphQL API` と `REST API` を `Node.js 22` の標準 `fetch` から呼び出す。

## 起動と直列化

同期処理は `issues` の `labeled` / `unlabeled`、5分間隔の `schedule`、`workflow_dispatch` で起動する。課題の変更通知では該当課題を確認し、定期実行と手動実行では `Project #4` の項目を全件読み取る。手動実行は `dry_run` を既定で有効にし、書き込み計画だけを出す。

`GitHub Actions` の定期実行は5分が最短間隔であり、高負荷時は遅延または欠落し得る。毎時00分を避ける時刻に設定する。個人用の `Project v2` は `webhook` で起動せず、課題表の変更は次の定期実行で検出する。

同じリポジトリの同期実行を `concurrency` で直列化し、実行中の処理は中止しない。これは同期処理同士だけを直列化する。人や別の API 利用者の同時編集はロックしないため、各書き込みの直前・直後に双方を再読込して競合を調べる。

## 項目と分類表示名

| 課題表の項目 | 値 | 課題に付ける名前 |
| --- | --- | --- |
| `Priority` | `P0` | `priority:P0` |
| `Priority` | `P1` | `priority:P1` |
| `Priority` | `P2` | `priority:P2` |
| `Priority` | `P3` | `priority:P3` |
| `Status` | `Backlog` | `status:Backlog` |
| `Status` | `Ready` | `status:Ready` |
| `Status` | `In progress` | `status:In progress` |
| `Status` | `保留` | `status:保留` |
| `Status` | `Blocked` | `status:Blocked` |
| `Status` | `Done` | `status:Done` |

変更する名前は上表の10個だけとする。上表にない名前は `priority:` / `status:` で始まっていても追加・削除せず保持する。課題表に未対応の選択値がある場合はその項目だけ同期を見送る。必須項目の欠落・重複・型違い、必要な選択値の欠落、課題表 ID の不一致、全件読込の未完了、保存情報の破損、権限不足など設定全体の異常は、どの項目も書き込む前に全体を停止する。

## 差分と競合の決定

`Priority` と `Status` は別々に同期する。各項目について、最後に確定した両側の値を保存する。課題表側には値と `ProjectV2ItemFieldSingleSelectValue.updatedAt`、課題側には現在有効な許可名と `timeline` 記録の `id`／`createdAt` を含める。

1. 保存情報がない初回は課題表を採用する。課題表が空欄なら対応する許可名を除去する。
2. 保存済みの値と現在値を比べ、片側だけ値・時刻・記録 ID が変わっていれば、その側を採用する。両側とも変わらない場合は何もしない。
3. 両側が変わったときだけ時刻を比較し、新しい側を採用する。同時刻・時刻不明なら課題表を採用する。
4. 課題表が以前から空欄で現在も空欄なら、課題表側の新しい変更とはみなさない。課題側だけが変わっていれば、その値を課題表へ反映する。
5. 課題表が空欄へ変わったときは値の `updatedAt` が存在せず、消去時刻を得られない場合がある。両側変更時は時刻不明として課題表を優先し、対応する許可名を除去する。
6. 課題表の項目を空欄へ同期するときは、その項目の許可名だけを除去する。課題側の許可名がすべて除かれたときは `clearProjectV2ItemFieldValue` で課題表の項目を消去する。

同じ値の再設定は、課題表の `updatedAt` または課題側の新しい `timeline` 記録 ID で観測できた場合に変更として扱う。すでに付いている同一名を再度付けても記録が作られない操作は検出できない。許可名が同じ項目に複数付いている場合は、現在有効な許可名のうち最新の追加記録を課題側の値とする。決定後に整理するときも許可名だけを変更し、未対応名は保持する。

## API 対象と保存情報

項目情報から `Project #4` の ID、`Priority`／`Status` 項目 ID、単一選択肢 ID を解決する。更新前に 課題表 ID、課題の種類、リポジトリ `ssaattww/RemoteDesktopMCP` の完全一致を確認する。課題 API の宛先もこのリポジトリに固定する。

同期状態は `project-label-sync-state` の専用分岐先にある `state.json` に保存する。内容は形式番号、対象の課題表／リポジトリ ID、項目 ID、課題番号、最後に確定した値・時刻・分類名の `timeline` 記録 ID、同期方向、確認時刻、処理中操作とする。課題の `title`／`body`、認証値、不要な個人情報は保存しない。公開リポジトリのため、保存情報と `GitHub Actions` の実行記録は公開情報として扱う。

初回の専用分岐先は `Contents API` では作らない。`POST /git/trees` で状態ファイルだけの木を作り、親なしの `POST /git/commits`、`POST /git/refs` の順に分岐先を作る。作成競合時は既存の参照を読み直して検証し、強制更新しない。通常更新では現在の参照先を親として木と `commit` を作り、期待 `SHA` を指定して `PATCH /git/refs/heads/...` に `force: false` で反映する。`SHA` 競合時は読み直して再判定するか、処理を失敗させる。

## 中断復旧と権限

各外部更新の前に、更新前の双方の値と意図を含む処理中記録を保存する。書き込み後に双方を読み直し、課題表値 ID／`updatedAt` または課題 `timeline` の追加・除去記録 ID を保存してから確定値を更新する。中断後は予定操作をそのまま再送せず、現在値を照合する。予定結果と一致すれば自身の更新として回収して確定し、その後の相手側編集を改めて判定する。課題表更新の応答を失い、人による同値設定と区別できない場合は自動更新と特定できないことがあり、判別不能時に課題表を優先する限界が残る。

課題表 v2 の認証値は `GitHub Actions` の `PROJECTS_TOKEN` からだけ使う。課題の分類名と保存情報の更新には `GITHUB_TOKEN` を使い、`issues: write` と `contents: write` のみを付ける。`contents: write` はリポジトリ全体の内容に及び、専用分岐先だけに制限される権限ではない。コードでは更新先を専用分岐先と `state.json` に固定し、強制更新しない。認証値・環境変数値・`request headers` は保存・出力しない。

## 変更なしの計画確認とテスト

計画関数は副作用のない形に分離する。手元で実行する `dry_run` は JSON 試験入力から予定変更を表示し、通信しない。手動起動の `dry_run` は読み取りだけを行い、課題・課題表・保存情報を変更しない。

偽応答を使うテストで、初回採用、両方向の片側変更、同時刻・時刻不明、空欄のままの課題表と課題側だけの変更、空欄を含む両側変更、同値再設定、自己更新の識別、中断後の処理中記録回復、許可名の重複、未対応名の保持、未知選択値の項目単位見送り、設定異常時の無書き込み、別課題表／リポジトリ／`pull_request` の拒否、書き込み前後の競合、`dry_run` 時の書き込み要求なしを確認する。実環境の課題表／課題への変更、同期処理の実行、本番用状態分岐先の作成は行わない。
