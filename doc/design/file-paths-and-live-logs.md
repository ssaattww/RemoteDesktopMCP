# ファイル操作の基準パスと使用者ログの更新

## 対象と実施順序

Issue #20 と #22 の設計。単一 PC の現行構成を対象とする。
設計書の修正を先に行い、実装は GPT-5.6 Terra high または GPT-6 Luna high、レビューは GPT-6 Sol high が担当する。

## ファイル操作の基準パス（#20）

`file_search`、`content_search`、`file_read`、`file_patch`、`file_transfer_*` は設定済み `root_id` を基準にする。
`relative_path` はそのルートからの相対パスであり、セッションの `working_directory` からの相対パスではない。
`process_start` は従来どおりセッションの `working_directory` で起動する。
既存呼び出しの書き込み先を変えないため、暗黙にセッション基準へ切り替えない。

`node_list` の各ノードに `roots: [{ root_id, absolute_path }]` と `path_base: "root"` を追加する。
既存の `root_ids` は互換性のため保持する。絶対パスは検証済みの設定ルートの実体パスを返す。
認証と本人の有効なセッションという既存の条件を維持する。
ツール説明、共通のパス入力説明、サーバーの利用説明にも基準の違いを記載する。

転送の upload begin、download begin、upload commit の成功応答に
`resolved_path`、`root_id`、`path_base: "root"` を追加する。
`resolved_path` は検証後の転送元または転送先であり、内部の一時ファイルや保存領域ではない。
サイズ・ハッシュ検証、パス逸脱と保護対象の拒否、原子的な確定という既存の動作を維持する。
検索の0件とバックエンドの失敗を混同しない。失敗を空の成功結果に置き換えない。

## ログ取得と通知（#22）

ログ本文は HTTP API で取得し、SSE は新着の通知だけを送る。
保存済み監査ログを正とし、接続ごとのファイル監視やログ本文の無制限な待機列を作らない。
使用者画面のページ全体を再読み込みする定期更新を廃止する。
従来の更新間隔設定はログ更新には使用しない。表示条件の保存とセッション詳細への移動は維持する。
操作履歴の時刻・状態・対象・識別子、コマンド・出力と実行目的の表示を維持する。
使用者の希望により、現在の画面描画を極力維持する。配色、余白、表の列、一覧と詳細の分離、
初期状態で畳まれた操作履歴、プロセスごとの時系列の出力、モバイル向けの表示を継承する。
新着ボタンと接続状態など必要最小限の表示を追加し、取得方式の変更を理由に画面を作り直さない。
使用者の追加希望として、各プロセスのコメント（実行目的）とコマンドは初期表示する。
出力は初期状態で折り畳み、使用者が開閉できるようにする。
差分反映時は既存プロセスの開閉状態を保持し、新しく現れたプロセスにだけ初期状態を適用する。

### 認証と対象範囲

`GET /api/logs` と `GET /api/events` は使用者コンソールの認証を必須にする。
画面用の名前空間に別名を設ける場合も、同一の認証処理と契約を適用する。
Cookie の送信対象を API に合わせ、旧 Cookie の移行とログアウト時の破棄を扱う。
未認証 API は JSON の401を返す。管理者権限だけでは使用者のログを返さない。
主体をクエリーから受け取らず、ログイン状態から決定する。
任意の `session_id` で本人の一接続へ絞り込める。他人のセッションは404とする。
セッション終了後の履歴も本人は閲覧できる。セッション作成前の操作も既存の所有者相関に従う。
SSE 接続中も認証期限、ログアウト、アカウントの許可取り消しを定期確認し、失効した接続を終了する。
キャッシュ抑止、同一オリジンの接続制限、表示値のエスケープを維持する。
画面のスクリプトを CSP で限定的に許可し、ログ本文を HTML やコードとして実行しない。

### GET /api/logs

- `limit` は既定100、1〜200の整数。それ以外は400。
- `before` は指定位置より古いログ、`after` は新しいログ。併用は400。
- 初回は両方を省略し、最新のページを取得する。
- 応答は `items`、`newestCursor`、`oldestCursor`、`hasMoreOlder`、`hasMoreNewer`。
- 本文の並びは新しい順。各項目は再取得時に重複排除できる安定した識別子を持つ。
- 時刻の一致に依存せず保存順に位置を定め、同時刻の記録を欠落させない。
- `after` の複数ページ取得は近い更新から順に進め、ページ間の記録を飛ばさない。
- `after` では未取得分のうち最も古いものから最大 `limit` 件を選び、その範囲だけ新しい順で返す。次は返却された `newestCursor` を使う。
- 空の初回にも通知開始位置を返し、最初のログ発生を検出できるようにする。
- cursor は不透明な値とし、主体と対象範囲に結び付ける。不正値は400。
- 保持範囲の外、ログ置換や再起動などで復元できない位置は409と `cursor_expired` を返す。
- 再同期は最新ページの取得で行う。本文取得失敗を空の成功応答にしない。

サーバーは監査ファイルから共有の索引を一度構築し、以後は保存成功後の追記を順序どおり反映する。
HTTP の各ページ取得や各 SSE 接続で監査ファイルを全走査しない。
索引には直近20,000イベントまで本文と所有者・接続・保存順の位置を保持する。
必要な所有者相関と開始時情報も有界に保持する。索引から外れた過去の位置は409とする。
起動時の読み込みは逐次処理し、全ファイルを一括でメモリへ読み込まない。
再起動またはファイル置換で索引世代を変更し、以前の cursor は409とする。
直近範囲を保存ファイルから復元するため、通常の切断では索引や記録を失わない。
この API の閲覧範囲は索引内の履歴とし、監査ファイル自体の保持期間は変更しない。
ブラウザーは最大1,000イベントを保持し、画面に上限を表示する。
永続化済みのログは一時的な SSE 切断では失わない。保持範囲内の位置から差分を取得できること。
取得単位は保存済みの追記イベントとする。操作の開始・終了や出力の追加を別の位置として扱い、
画面側で操作 ID とプロセス ID ごとにまとめる。以前から存在する操作の終了も新着として取得する。
ページをまたぐ操作に必要な開始時刻、コマンド、実行目的は、本人の保存済み記録から補う。
未取得の開始イベントを仮定して別人の情報を補完しない。

### GET /api/events

`Content-Type: text/event-stream` とし、1画面につき1本接続する。
`after` は画面が反映済みの最新 cursor。再接続でも通知の最新位置ではなく、この位置を使う。
新着の反映でこの位置が進んだら旧 EventSource を閉じ、新しい `after` で接続を作り直す。
接続を同時に複数残さず、閉じた接続の遅延イベントは世代を確認して破棄する。
`logs-available` のデータは `addedCount`、`latestCursor`、`overflow` のみとし、本文を含めない。
接続時に既存の未取得分を通知し、以後100〜500msで追加分を集約する。
一接続内の `addedCount` は前の通知以降の増分とし、初回は `after` 以降の差分件数を通知する。
ブラウザーは接続ごとの通知件数を管理し、再接続初回の通知を以前の件数へ重複加算しない。
件数は1000件で表示を打ち切り、上限以上は `overflow` を立てる。
差分位置が失効した接続には再同期が必要なイベントを送り、無限再接続を避ける。
heartbeat は20秒を標準とし、15〜30秒の範囲で行う。

ログ収集と更新監視はサーバーで共有する。通知のためにクライアント数だけ全ログを読み直さない。
変更のない状態で全ファイルを繰り返し走査しない。永続化成功後の更新だけを通知対象とする。
遅い接続には有界な待機または切断を適用し、切断後は保存済みの位置から復旧する。
接続終了時とサービス終了時にタイマー、購読、応答を解放する。

## 画面の状態と更新競合

接続状態は `connecting`、`connected`、`reconnecting`、`disconnected` を表示する。
ログ状態は `current`、`pending`、`refreshing`、`resync-required` を管理する。
新着通知だけでは本文もスクロール位置も変えず、更新ボタンの新着件数だけを更新する。
使用者の追加希望により、ボタンは「↻ 更新（新着 N件）」とし、新着がない場合も「0件」で表示する。
上限時は「1000件以上」とする。切断中も既存のログを読めるようにする。
更新操作はページ先頭のヘッダーではなく、現在表示している最新の実行コマンド・ログの直上に配置する。
更新と新着件数を一つのボタンにまとめ、コマンドがまだない場合もその位置を用意する。
ボタンと最新ログの下引きは同じ更新処理を実行し、新着が0件でも状態を再取得する。
セッション一覧では一覧の直上に同じ更新操作を配置する。
スマートフォンでは、ログ一覧の先頭にある最新ログそのものを下に引いて離す操作でも新着と状態を更新できるようにする。
更新操作領域を引く方式にはしない。最新ログの先頭が見えている状態でそのログ上から始めた下方向の操作を対象とする。
過去ログや、長い出力の途中を読んでいる位置からの操作は通常のスクロールとして扱う。
引いている間は操作の案内を表示し、十分な距離に達した場合だけ更新する。
通常のスクロール、横方向の操作、キャンセル、取得中の重複操作では更新しない。
キーボードとマウスでは引き続きボタンを利用できるようにし、引く操作だけを必須にしない。

ボタン押下時に反映済みの最新 cursor を `after` として本文を取得する。
ページが複数ある場合も欠落なく順に取得し、本文はブラウザーの上限内で保持する。
取得中の通知を無条件に消さず、反映済み位置を確定してから通知を再同期する。
失敗時は本文と cursor を保持して `pending` に戻し、再試行できるようにする。
cursor 失効時は `resync-required` とし、ページ全体を再読み込みせず最新ページを取得する。
過去方向のスクロールでは `before` で追加取得する。これは新着状態を解除しない。
過去取得と新着反映が競合しても重複や位置の巻き戻りが起きないようにする。
メモリ上限で古い項目を除く場合、続きを再取得できることと画面での上限表示を両立する。

### ログ以外の表示

セッション一覧、実行中件数、停止状態は取得時点の情報であることを最終取得時刻とともに表示する。
「状態を更新」操作で HTTP から現在の本人の状態を取得し、必要な表示領域だけを更新する。
ログの新着反映時にも状態を更新する。状態取得だけで既存ログやスクロール位置を変更しない。
停止・再開は従来の認証済み HTTP 操作とし、その応答で現在の状態を反映する。
古い READY 表示を現在の実行可能性の保証として扱わず、実行可否の判断はサーバーで継続する。

## 検証

### CI の Windows テスト時間

Windows の Node.js 22 テストは標準の `--test-shard` で3分割し、全テストファイルを各 shard に一度ずつ割り当てる。shard ごとに診断 artifact 名を分け、1 shard の失敗で残りを停止しない。型検査・ビルドは既存の Windows 検証として各 shard で実施し、簡潔な同一ジョブ構成を保つ。workflow の concurrency group は同じ PR またはブランチの古い実行をキャンセルする。変更後は YAML 構文、Node 22 の shard オプション、shard ごとの対象一覧と artifact 名を軽量に確認し、重いテスト一式を開発端末では再実行しない。

Windows の CLI と bootstrap のセキュリティ回帰試験では、PowerShell ACL 検証を含む子プロセスが完了するための hang guard を15秒とする。これは処理速度の性能基準ではなく、完了しないプロセスを止める上限であり、危険な ACL の拒否、異常終了、秘密値を出さないという機能 assertion は維持する。

CI では性能測定だけの subtest を明示的に skip し、通常のローカル `npm test` では実行する。CI は再試行の回数上限、fail-closed、状態・監査などの機能契約を検証し、ACL やプロセス起動を含む壁時計時間を合否にしない。ローカル性能 subtest は対象の retry phase や停止要求だけを測り、初期化全体を測らない。認証期限、heartbeat、受信期限、停止確認のように製品契約そのものを検証する時間は、この原則と区別する。

- セッションの作業ディレクトリと root が異なる条件で、列挙・検索・読取・編集・転送の基準を確認する。
- begin と commit の実際のファイル位置と応答の一致、既存のパス保護の回帰を確認する。
- ページ境界、同時刻、空からの追加、複数ページの新着、無効・失効 cursor と本人だけの取得を確認する。
- SSE の本文非包含、集約、heartbeat、切断回収、再接続、失効・ログアウト、遅い接続を確認する。
- 通知のみでは本文・スクロールが変わらないこと、取得中の追加・失敗・過去取得の競合を確認する。
- 型検査、Lint、ビルド、既存試験と追加回帰試験を行い、未実施の環境・画面確認は区別して報告する。
