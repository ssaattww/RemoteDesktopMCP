# 作成済みセッション情報の後編集

## 目的と範囲

作成済みセッション情報の後編集を設計する。作成済みの本人所有セッションについて、作業ディレクトリと用途を使用者画面から編集し、保存内容を再表示できるようにする。編集APIは使用者画面の認証済み経路に限る。初回実装はこの二項目に限り、外部URLと題名はPR52の共有処理を統合するまで受け付けない。

課題9はセッション作成時に作業ディレクトリと用途を設定する。この設計はその後編集と実行中プロセスとの整合を扱い、セッション作成契約、ファイル操作の基準位置、実行権限、実行先の割当を広げない。

## 現行実装と境界

- `src/index.ts` の `Session` は識別子、所有者、作業ディレクトリ、用途、有効期限、状態を保持し、セッションはプロセス内の `sessions` に置かれる。セッション情報はサーバー再起動を越えて復元されない。
- `session_open` は絶対パスを `realpath` で正規化し、その場所がディレクトリであることを確かめている。作業ディレクトリは設定済みファイルの基準場所の内側に限定されず、`process_start` はサーバーのOS利用者が既に持つ権限でコマンドを起動する。更新も作成時と同じ範囲を守り、新しいパス許可一覧、ファイル権限、コマンド権限を作らない。ファイル操作の `relative_path` は引き続き `root_id` 基準であり、作業ディレクトリを基準にしない。
- 現在のセッション利用と `node_list` は本人の有効セッションを求め、ノードはサーバーで構成された一つのノードに固定される。後編集は所有者やノードを変更する手段にしない。
- この設計の基点 `main` は一つの同じ機器上の実行環境で動作し、セッションに遠隔実行先は保持しない。実装をこの基点から開始する場合の検証先は同じプロセスのOS環境とする。
- PR28は未統合で、別機器上の実行先を持ち込む別作業である。PR28統合後にこの機能を実装する場合は、セッションに固定済みの実行先へ更新を送り、作業ディレクトリの `realpath`、ディレクトリ確認、権限確認をその実行側OS上で行う。統括側の同名パスで代用しない。版番号の比較と情報変更はセッションを所有する実行側で原子的に行い、`process_start` も同じ側の直列化境界で開始時の作業ディレクトリを取得する。実行側が未接続、または更新操作を提供しない場合は `503 executor_unavailable` または `501 unsupported_executor_operation` で拒否し、同じ機器での実行へ切り替えない。利用者が実行先の割当を編集できるようにはしない。
- `src/user-console.ts` は既存のログイン認証、画面専用トークン、同一生成元の確認で変更要求を保護している。`/api/console-state` は監査履歴と本人の稼働中セッションを返す。新しいURLと題名もこの所有者境界内だけで取得できるようにする。
- `session.open` の監査記録は現在、作業ディレクトリと用途を含む。課題48の変更記録は値を重ねて記録せず、変更項目名と版番号だけを残す。外部URL、URLの照会部・断片部、表示題名は監査、エラー、診断、通知へ複製しない。

## 使用者画面

- 稼働中セッションの一覧に「編集」を置き、作業ディレクトリ、用途、任意URL、任意題名をまとめて編集する。保存前に変更内容を確認できるようにし、作業ディレクトリを変えた場合は「保存後に開始するプロセスから適用。既に起動中のプロセスは開始時の場所を継続」と表示する。
- 外部URL欄と題名欄はこの実装段階では表示しない。PR52の共通処理と契約を取り込んだ後に、後続の統合設計で追加する。秘密を含むURLの扱いはPR52の契約に従い、URLを監査、エラー、診断、通知へ複製しない。
- PR52の共有処理を統合した後の画面では、手入力題名がある場合に題名を優先して自動取得しない。題名がある一覧行ではURL文字列を隠し、題名全体を右側の案内として表示する。案内は現在画面を保って別の閲覧画面で開き、`target="_blank"`、`noopener noreferrer`、`no-referrer` を設定する。題名やURLは文字列として安全に扱い、遷移前にURLを再検査する。
- 保存成功時は `/api/console-state` を再取得して表示を更新する。現在の入力位置、選択、開閉、一覧表示位置を保つ。失敗時は編集中の入力を保持し、理由を示す。保存成功前の入力値を他の表示領域へ先行反映しない。
- 版競合の409では最新状態を別の比較表示として読み込み、未保存の入力とその入力元版を保持する。最新取得やPR51の自動更新で編集中の欄を上書きしない。利用者は「自分の入力で再編集」を選び、競合項目ごとに比較・修正してから最新版番号で保存するか、「最新値を取り込む」を明示的に選んで入力欄の値を置き換える。どちらの選択も自動再送せず、最終保存は利用者の操作を要する。
- 終了済み、期限切れ、緊急停止で閉じたセッションには編集操作を示さず、古い画面から要求された場合も拒否する。編集操作はセッションを再開しない。

## API契約と認可

使用者画面専用の `PATCH /api/sessions/:sessionId` を追加する。リクエスト例のJSON値は契約の実データ名である。

```json
{
  "expectedVersion": 3,
  "workingDirectory": "D:\\work\\project",
  "purpose": "作業内容"
}
```

- ログイン済み利用者の識別子は既存のログイン認証から取得し、要求本文の利用者名は認可に使わない。対象セッションを取得して所有者と稼働状態を確認してから、検証も更新も行う。他人の識別子は存在の有無を明かさない404とする。ログイン失効時は既存のログイン要求へ誘導する。
- 更新要求は同一生成元からの送信に限り、画面用トークンを必須にして別経路からの偽装更新を防ぐ。受け付ける項目は作業ディレクトリと用途だけとする。`externalUrl` と `externalTitle` はPR52の共有処理との統合まで未対応項目として `400 unsupported_field` で拒否する。所有者、実行先、セッション識別子、有効期限、状態を変更する項目や未知の項目も拒否する。
- `expectedVersion` は必須の非負整数とする。セッションの `version` と一致しなければ409 `version_conflict` とし、変更を一つも適用しない。応答は再読込に必要な現在版番号だけを返し、秘密値をエラー本文に含めない。
- `/api/console-state` の本人向け稼働中セッション項目には、`working_directory`、`purpose`、`version` を含める。この実装段階では外部URLと題名に関する項目を返さない。終了済み履歴にはセッションを含めない。
- 成功応答には新しい版番号と現在の本人向け作業ディレクトリと用途を返す。URLと題名はPR52の共通処理を統合した後、本人の稼働中セッション応答だけに追加する。値の形式・長さ不正は400 `invalid_request`、存在しない・他人所有・終了済み・期限切れ・停止中のセッションは同じ404 `session_unavailable` とし、部分保存しない。未ログインは401、画面用トークンまたは生成元検証失敗は403、版競合は409とする。エラー応答に入力値を含めない。

## 入力検証と一括更新

- `workingDirectory` は空でない絶対パスとし、上限は作成APIと同じ4096文字とする。更新時に `realpath` とディレクトリ実体を再確認し、存在しない場所、形式不正、通常のプロセス起動で利用できない場所を拒否する。正規化後のパスを保存する。サーバーOSの利用者権限を越える実行を認めず、設定済みファイルの基準場所の外を新たに拒否する規則も加えない。パス確認後に場所が消失・権限変更された場合は、該当プロセスの起動失敗として扱う。
- `purpose` は前後空白を除き、作成APIと同じ1〜200文字とする。空にして必須項目を消す更新は拒否する。
- PR52統合後に扱う外部URLと題名の長さ、許可方式、安全な題名取得、転送先の再検査、HTML安全化は課題45とPR52で確認する契約を再利用する。外部URLは2048文字以下、題名は200文字以下。URLの認証情報欄形式の利用者名とパスワードを含むURLはURL全体を破棄し、題名のみ保持できる場合も外部取得は行わない。任意の照会部値や階層部分値を秘密と識別して自動で除くことは保証しない。URLへ秘密を含めないよう説明し、受け入れたURLは本人の稼働中セッションに限って保持する。自動題名取得は題名上書きが指定されていない場合だけとする。
- PR52統合後に共有項目を扱う場合、部分更新で省略された項目は維持する。入力欄表示だけでは変更意図と見なさず、取得元も保存状態に含めて扱う。`externalTitle` を省略した場合は題名の変更を要求していない。URLが変わらなければ題名と取得状態を維持する。URLが変わり、現題名が `manual` なら手入力題名を維持する。`externalTitleSource` が `manual` 以外（`fetched` または未設定）なら旧URL由来の題名と取得結果を破棄し、題名と取得元を未設定にする。新URLの取得が可能なら `externalTitleStatus: pending`（取得元は未設定）とし、取得対象でなければ `externalTitleStatus: not_requested` にする。`pending`、`failed`、`not_requested` は取得状態であり、取得元ではない。`externalTitle` に文字列を明示した場合だけ手入力題名として `externalTitleSource: manual`、`externalTitleStatus: resolved` にする。`externalTitle: null` または明示した空文字は手入力上書きを解除し、題名と取得元を未設定にする。取得可能なURLなら取得元未設定の `externalTitleStatus: pending` から自動取得を始め、取得しない場合は `externalTitleStatus: not_requested` とする。URL・題名を変えない作業ディレクトリと用途だけの要求は既存の取得状態に触れない。
- 変更項目を全て構文検証し、パス検査とURL・題名検査を終えてから候補データを作る。セッション情報用の直列化区間で、再度所有者・状態・`expectedVersion` を確認し、全項目と新しい版を一括で適用する。一項目でも失敗すれば元の値、版、題名取得状態を保つ。同一値だけの要求は値も版も変えずに成功として返せる。

## 版番号、外部URL情報の取得、競合

- `version` は作成時1とし、成功したメタデータ変更ごとに1増やす。画面は取得した版番号を `expectedVersion` に添える。連続編集で古い画面から上書きした場合は409とし、画面は最新状態を取り直して利用者に再編集を促す。
- PR52の共有契約は `externalUrl`、`externalTitle`、取得元 `externalTitleSource`（`manual`、`fetched`、未設定）、取得状態 `externalTitleStatus`（`pending`、`resolved`、`failed`、`not_requested`）、取得競合用 `linkRevision` とする。題名が手入力済みなら通信しない。題名が未指定で取得可能なURLがある場合だけ非同期取得を開始し、更新応答は取得完了を待たない。
- URLを変更する利用者編集、または題名を手入力・解除する編集では、一回につき `linkRevision` を一度増やす。手入力題名と同じ文字列を明示して取得結果から手入力へ切り替える操作も編集として扱い、改訂番号を一度増やして自動取得を停止する。同じURLと手入力済みの同一題名を再送しただけなら変更なしとし、改訂番号も版番号も増やさない。 手入力題名を明示解除したとき、URLが有効なら取得元を未設定にして取得を開始し、URLがなければ `not_requested` とする。
- URLと題名はセッション本体と同じ揮発性・本人限定の寿命に置き、別ファイルや監査記録に保存しない。セッション終了、期限切れ、緊急停止では外部URL、題名、取得状態を直ちに消す。サービス再起動時はセッションとともに失われる。

## 実行中プロセスと作業場所

- `process_start` はプロセス開始前に、所有者確認済みセッションの現在の正規作業ディレクトリを開始時の確定値として取得する。この取得とメタデータの一括更新は同じ直列化境界で順序付ける。プロセス起動後のセッション変更は、開始済みプロセスの作業場所を遡って変えない。
- `Process` に開始時の `workingDirectorySnapshot` を保存し、プロセス開始監査にも開始時の作業ディレクトリを記録する。画面や履歴に現在のセッション作業ディレクトリとプロセス開始時の値を並べて示す必要がある場合は、それぞれの表示名と時点を明示する。プロセス出力や状態取得は既存どおりプロセス識別子を使い、別の場所に移動しない。
- 更新後に開始する `process_start` は新しい作業ディレクトリを使う。ファイル操作、転送、`node_id`、ノード選択、OS権限には影響しない。セッションとプロセスの関連付けは維持する。

## 監査と通知

- 成功した編集は `session.metadata.updated` を一件記録する。記録項目は `user`、`sessionId`、`previousVersion`、`version`、`changedFields`、日時とする。作業ディレクトリと用途も更新記録には値を含めない。失敗記録を記録する場合も失敗分類、対象利用者、セッション識別子に限り、入力値、エラー本文、URL、題名を含めない。
- 既存の通知経路は値を含まない `session.metadata.updated` の発生だけを知らせる。通知本文はセッション識別子、版番号、変更項目名に限る。使用者画面は認証済み `/api/console-state` を取得し直して表示する。URLや題名を画面通知や操作履歴通知、エラー表示へ載せない。
- 非同期題名取得の完了は監査記録を作らず、値のない変更通知だけで画面へ反映する。所有者の有効セッションAPI応答に限って最新値を読み出す。終了後の監査・操作履歴にURLと題名を残さない。

## 終了・期限切れ・停止時の扱い

編集を許可するのは状態が `active` で、期限内であり、所有者が現在ログイン中、かつ緊急停止が有効でないセッションだけとする。終了、期限切れ、緊急停止のどれかと更新が競合した場合は同じ直列化境界で先に確定した遷移が勝つ。閉じる遷移が先なら更新を拒否し、更新が先なら監査を一件記録した後、終了側の処理でURLと題名を消す。停止を解除しても既存セッションは再開せず、新しいセッションが必要となる。過去の監査履歴は既存の保持規則に従うが、秘密のURLと題名は記録しない。

## 関連機能との整合

- 課題45は作成時の任意URL・題名、手入力優先、自動取得、安全なURL表示を扱う。課題48は同じ項目と安全規則を編集へ再利用し、値の保持先と所有者境界を変えない。
- PR52は別途進行中の共有設計であり、URL・題名の共通処理と契約を再利用する。今回の実装に重複したURL取得機能を作らない。

## 実装時のテスト計画

作業ディレクトリ、用途、版番号の初回範囲は、先に追加した試験で失敗を確認してから実装し、現在は合格を確認済みである。`test/user-console.test.ts` は認証、画面用トークンと生成元確認、所有者境界、未対応URL項目、入力拒否、変更監査、版競合、並行更新、終了・期限切れ・停止時の拒否を確認する。別の回帰試験では更新と `process_start` の順序を制御し、開始前後の実行先と開始監査に開始時の値が残ることを確認する。`test/user-console-client.test.ts` は成功時の表示更新と版競合時の未保存入力保持を確認する。以下は追加境界と後続統合の計画である。

1. `test/mvp.test.ts` または `test/regressions.test.ts` に、必須値・長さ境界、絶対パス、存在しない場所、ファイル拒否、OS利用者がアクセスできない場所の追加確認を行う。保護OSパスを使わず、試験用に差し替えた構成で拒否を検証する。失敗時に全項目と版番号が元のまま残ることを確認する。
2. 別機器上の実行先対応を統合済み `main` が含む場合は、統括側に存在しないパスでも実行側に実在するパスを受け入れること、統括側だけに存在するパスを拒否すること、実行側未接続・非対応時に同じ機器での実行へ切り替えないこと、実行側の版比較・作業場所検証・処理開始時の確定値が同じ実行主体に属することを試験する。
3. URL情報の後続統合試験は、PR52の確定契約を共有した後に追加する。URLの認証情報欄の拒否と照会部・階層部分の値から秘密を自動判定できないことを確認する。手入力題名で通信しないこと、未指定の場合だけ取得すること、取得中のURL変更や終了後に古い結果を適用しないことを確かめる。通信処理を差し替え、外部ネットワークへ接続しない。
4. 共有URL処理の統合後は、保存値を監査、失敗応答、通知に含めず、通知後の所有者向け状態再取得でだけURLと題名を得られることを確認する。閉じる、期限切れ、緊急停止でURLと題名が消え、停止解除後も既存セッションを編集・再利用できないことを確認する。
5. `test/user-console-client.test.ts` に、取得済み題名の未編集保存、`manual` / `fetched` の取得元維持、題名を含めないURL更新、手入力題名の維持・明示解除、URL変更時の再取得を追加する。版競合後の最新状態読込では未保存値を保持し、自動更新で入力欄を上書きせず、利用者が選択した後だけ最新値で再保存できることを確認する。
6. 監査/API試験では保存値を監査、失敗応答、通知に含めず、更新通知後に所有者の状態再取得でだけURLと題名を得られることを確認する。閉じる、期限切れ、緊急停止でURLと題名が消え、停止解除後も対象を編集・再利用できないことを確認する。
7. `test/user-console-client.test.ts` に取得済み題名の未編集保存、`manual` / `fetched` の取得元維持、題名を含めないURL更新、手入力題名の維持・明示解除、URL変更時の再取得を加える。版競合後の最新状態読込では未保存値が残り、自動更新が入力欄を上書きしないこと、再編集または最新値取込を利用者が選んだ後だけ変更され、最新版で再保存することも確認する。

実装後の関連確認は `node --import tsx --test test/mvp.test.ts test/regressions.test.ts test/user-console.test.ts test/user-console-client.test.ts`、続いて `npm run check`、`npm run lint:ts`、`npm run lint:md`、`npm run lint:md:terms:design` とする。依存の導入が必要なら、既存の `package-lock.json` を使う `npm ci` について事前に利用者確認を得てから行う。実装の統合確認では Windows環境の自動確認 と認証済みAPIの回帰を含め、実ネットワークへ接続しない合成データを使う。

## 保留する設計判断

- PR52の共有処理は後続統合の前提である。設計案に示された契約に合わせ、統合時には同じURL・題名処理を再利用する。
