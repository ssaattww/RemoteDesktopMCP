# 共有作業一覧と更新期限による操作制御

## 状態

課題 #56 の設計。利用者選択により、作業一覧はセッション単位、強制機能は各セッションで初期有効、有効化直後は5分猶予とする。本書ではこの決定を仕様として具体化し、対象外の実装詳細と環境確認事項を区別する。

## 目的と配置

認証済み利用者とチャットが同じ作業一覧を読み書きし、残作業、完了済み項目、進捗を共有する。作業一覧は既存の使用者画面にある `/user/sessions/:sessionId` のセッション詳細画面の先頭に置く。一覧画面や初期画面を配置先にしない。

各項目は識別子、本文、状態（未着手・進行中・完了）、並び順、作成者、作成時刻、更新時刻を持つ。更新は項目の追加・編集・状態変更・削除を含み、成功した変更だけを一覧全体の更新時刻と単調増加する版番号に反映する。画面と MCP の読み取りは同じ保存済み状態を返し、更新応答には新しい版番号とサーバー時刻を含める。競合する更新は期待版番号を照合し、不一致なら変更せず最新状態を返して再読込を促す。

## 決定済みの選択: 適用範囲と初期値

| 選択 | 採用値 | 代替 | 根拠と互換性 |
| --- | --- | --- | --- |
| 作業一覧の適用範囲 | セッション単位 | 利用者単位、担当者単位、複数セッションで共有する作業単位 | セッション詳細上部という配置と既存の `session_id` 所有・認可境界に一致し、別作業の完了状態が混ざらない。セッション単位では新しいセッションに一覧を引き継がない。利用者単位なら複数セッション間で共有できるが、同時作業が混ざり、一覧・履歴の意味と認可 API の範囲を広げる。担当者単位は現行モデルに担当者識別子がないため、追加の権限モデルを要する。 |
| 強制機能の初期値 | 有効 | 無効 | 有効は各セッションの作成直後から作業一覧の更新を促す。空の一覧を含めてセッション作成時から5分の猶予を数え、その後は作業一覧を更新するまで通常操作を拒否する。利用者はいつでも無効にでき、無効中は経過時間で拒否しない。無効を初期値にすると既存の通常操作を止めないが、利用者が毎回有効にする必要がある。 |

セッション単位・初期有効は利用者が選択した仕様である。作業一覧と強制設定は同じセッションに属し、担当者単位の共有や別セッションへの引継ぎは行わない。実装開始前の独立した設計確認で選択との整合を確認する。

## 更新時刻、時計、失敗

- 経過時間の権威はサーバー単調時計とし、表示・監査にはサーバー壁時計による協定世界時の文字列を使う。クライアント時計は判定に使わない。
- 強制機能が有効な場合、通常操作を委譲する直前に `nowMonotonic - lastTodoUpdatedMono >= 300_000` を期限超過と判定する。境界値ちょうどから拒否する。画面側の時間表示は説明だけに使い、執行判断は必ずサーバー側で行う。
- 推奨する起動中のみの状態保存では、一覧の更新は検証後に内容、版番号、単調時計値を `todoLock` の下で一度に差し替える。版番号の不一致、権限違反、入力検証失敗は状態を変更せず、更新時刻も進めない。処理が差替え前に失敗した場合、内容と更新時刻は旧値のままにする。
- 有効中に更新単調時計値が欠落する、単調時計の読み取りに失敗する、または壁時計と単調時計の差が異常と判定された場合は通常操作を拒否し、作業一覧を更新して基準時刻を再確立するよう案内する。作業一覧の管理と安全例外操作は継続可能にする。異常理由は監査する。
- `Map` 差替えに失敗した場合は更新応答を失敗とし、版番号と更新時刻を進めない。再起動時はセッションと同様に一覧状態が失われる。再起動をまたぐ保存方式は代替として別に示す。

## 有効・無効の切替と猶予

無効では時間経過を理由に通常操作を拒否しない。有効・無効は権限確認後に明示的に変更し、変更者、時刻、セッション、変更前後を監査する。

初期有効のセッションは作成時の `enabledAtMono` から5分の猶予を開始する。無効から有効へ切り替える時も、過去の一覧更新時刻が古くても即時に拒否せず、その切替時刻から5分の猶予を開始する。有効中は「最後の一覧更新」と「今回有効にした時刻」のうち後の単調時計値から5分後に拒否する。式では `nowMonotonic - max(lastTodoUpdatedMono, enabledAtMono) >= 300_000` と表せる。`max` は二つの時刻の後者を選ぶ意味である。有効化後に一覧更新が成功すれば、その更新単調時計値から通常の5分期限を数え直す。したがって、切替時刻からの猶予は、切替後に作業一覧を更新しない場合は5分で終わり、更新した場合は更新時点から新たに5分となる。無効にすると猶予・期限による拒否を解除する。有効へ戻すたびに新しい `enabledAtMono` を記録する。

## 適用点と例外操作

判定位置は、認証、セッション所有者と状態の検査、使用者の緊急停止の検査を済ませた後、Desktop Commander などの通常処理へ渡す直前とする。クライアント画面だけで制御しない。既存の認可が通った後に追加条件として評価し、一覧の操作から所有者境界を迂回できない。

作業一覧の管理操作は常に制御対象外とし、一覧を直すための呼出しが自己拒否しないようにする。緊急停止は既存の使用者緊急停止経路を維持し、期限制御を通さない。

推奨する狭い安全例外は次のとおり。例外は固定されたサーバー側操作名と対象所有権で判定し、引数の `force`、自由記述、呼出し元申告、名前の接頭辞では例外にしない。

- `process_kill` は同じ利用者と同一セッションに属し、実行中または停止未確認の処理だけを停止できる。再要求を直列化し、2秒未満の重複要求と終了済み処理への要求を拒む。
- `process_status` と `process_output` は同じ利用者と同一セッションが所有する記録済み処理に限って許可する。期限超過後は監視処理の保存済み状態・出力を返し、下流への状態取得・出力読取を起こさない。所有確認のない任意状態確認には広げない。
- 転送取消は同じ利用者と同一セッションが所有する未完了転送の後片付けに限って許可する。
- セッション終了は既存の認可と終了時の後片付けを維持し、期限状態を理由に拒まない。

それ以外のファイル操作、プロセス操作、新規起動は通常操作として判定する。安全例外の実際の操作名と終了状態の根拠は現行 API を調査して固定し、判定不能な場合は例外を広げず、作業一覧の更新を案内する。例外が拒否・失敗しても通常操作を自動再試行しない。

## 拒否応答、監査、画面

期限超過による拒否は機械判定可能な結果名、理由（未更新から5分以上）、最後の更新時刻または欠落状態、一覧の表示・更新方法を含める。一覧を更新して再実行する手順を示すが、拒否された呼出しを後から自動実行しない。

監査記録は作業一覧の作成・更新・削除、有効・無効、制御の許可・拒否、例外許可、保存失敗を記録する。利用者、セッション、版番号、サーバー時刻、操作名、理由を含め、一覧本文の全文は既存操作記録へ複製しない。一覧の読取は必要以上に本文を監査へ複製しない。管理者の監査境界を広げず、作業内容は認可された利用者用セッション画面とチャットにのみ返す。

セッション詳細の先頭に作業内容、完了数と総数、最終更新時刻、強制状態、有効・無効切替、更新失敗または競合からの回復案内を表示する。更新後は版番号を同期し、別画面やチャットの古い版番号による上書きを拒否する。

## 互換性と移行

作業一覧の状態がないセッションは空の一覧とし、強制機能は有効として初期化する。初期化時刻を `enabledAtMono` に記録し、その時点から5分の猶予を与える。一覧記録のない状態を理由に即時拒否しない。セッション状態はサーバーの起動中だけ保持し、サーバー再起動後に旧セッションIDは再利用できないため、再起動時の既存セッション移行はない。認証、接続識別子、ツール引数、所有者境界、緊急停止の既存仕様は維持する。強制機能は利用者がセッション詳細から明示的に無効にできる。

## 現行実装に基づく具体案

### 保存先と寿命

現在の実行セッションは `RemoteDesktopService.sessions` の起動中だけ保持する `Map` で管理され、サーバー再起動後に古い `session_id` は再利用できない。緊急停止状態だけは `DATA_DIR/user-execution-states.json` に保存し、一時ファイル `.next` の同期後に置換している。監査は `DATA_DIR/audit.jsonl` へ追記し、非公開アクセス権を検証している。

推奨案は作業一覧と強制設定を起動中の同一セッション状態に保持し、`session_id` をキーとする `Map` とすること。更新と強制判定を一つの `todoLock` の下で行い、更新候補を検証してから内容、版番号、経過時間基準を一度に差し替える。セッション終了・期限切れ後は、既存のセッション履歴が起動中に保持される期間だけ画面用の読取状態を残し、更新・強制は停止する。HTTP 接続をまたいで利用でき、再起動時にはセッションと同じく破棄される。保存媒体に残る監査記録から作業本文を復元しない。

代替として `DATA_DIR/todos.json` にセッション ID 単位で保存する方式がある。既存の非公開 JSON 状態と同様に一時ファイル同期、置換、アクセス権保護を行えるが、現行のセッション ID は再起動後に無効となるため、記録だけが残る。履歴画面で再表示する追加要件が決まらない限り、不要な残存記録と清掃責務を増やす。サーバー再起動をまたいで作業一覧を保持する要件が必要なら、まずセッション再開・履歴表示との関係を別途設計してから永続化を選ぶ。

### API 名と所有確認

現行 API に作業一覧の画面接続先や MCP 操作はない。名称候補は MCP の `todo_get(session_id)`、`todo_update(session_id, expected_version, changes)`、`todo_enforcement_set(session_id, enabled)` とする。画面用にはログイン必須の `GET /api/sessions/:sessionId/todo`、`PUT /api/sessions/:sessionId/todo` を候補とし、書込み要求には既存の完全一致送信元確認と `x-csrf-token` ヘッダー検証を適用する。画面からの項目更新と強制設定の変更は同じ要求で行わず、強制設定は MCP 操作と `RemoteDesktopService` の共通処理で更新する。

MCP 側は `session(user, session_id)` と同じ使用者・有効セッション検査を通す。画面側も `userLogin` 後に同じセッション所有確認を行い、他人のセッション ID は既存と同様に存在を明かさず 404 とする。チャットと画面の更新は `RemoteDesktopService` の共通処理に集約し、画面だけに強制判定を置かない。

### 時計の異常検知

5分の経過判定には `Date.now()` と `node:perf_hooks` の `performance.now()` を組み合わせる案を推奨する。最後の作業一覧更新は壁時計表示値と単調時計値の両方を記録する。評価ごとに両時計の経過差を比べ、壁時計が逆行する、または両時計の経過差が60秒を超える場合は `todo.clock_anomaly` を監査し、異常状態中は通常操作を拒否する。利用者が作業一覧を正常更新すると新しい基準を両時計で確定し、異常状態を解除する。単に時計が2回正常に進んだだけでは古い更新時刻を新しい時刻に見せない。作業一覧の更新、設定変更、緊急停止、終了確認、後片付けは異常中も可能にする。

作業一覧とセッションが再起動時に失効する候補では、単調時計値を保存媒体へ保存・復元しない。監査や表示の日時にはサーバー壁時計の `ISO 8601` 文字列を使うが、同一プロセス内の経過判定は単調時計を使う。単調時計が OS の休止時間を数えない環境では復帰時に2時計の差を検出し、作業一覧の更新まで通常操作を拒否する。利用環境で単調時計が休止時間を含むかを確認できない場合は、壁時計を基準にし、検知可能な逆行や不連続があれば作業一覧の更新まで通常操作を拒否する案を代替とする。

### 監査失敗時

現行の `audit()` は `audit.jsonl` への追記やアクセス権確認が失敗すると例外を返す。現在の共通操作受付は受信・開始・終了を記録するため、監査故障が操作の開始前または副作用後の応答へ影響する。緊急停止は監査失敗を個別に捕捉して停止処理を続ける。

推奨案は共通 `this.tool` 受付にサーバー側の固定操作規則を設けること。認証、`session` 所有権確認、緊急停止確認の後、処理関数を呼ぶ前に操作を通常操作か固定例外か分類する。通常操作は強制判定を行い、強制中の許可判断記録 `todo.gate_allowed` を記録できた時だけ下流へ委譲する。記録に失敗した場合は `TODO_GATE_AUDIT_UNAVAILABLE` を返して副作用を起こさない。期限超過の拒否自体は監査書込みに失敗しても維持し、`TODO_STALE` を返す。強制無効中は期限制御の許可監査を要求しない。

作業一覧の読取・更新と有効状態の切替、緊急停止、所有確認済みプロセス停止、終了確認、転送取消、セッション終了は固定例外候補とし、監査記録失敗だけを理由に制御で拒否しない。したがって例外は処理関数内の `audit()` 例外捕捉だけでは実現できない。共通受付が `operation.received` または `operation.started` を書けない場合も固定例外の処理関数へ進め、監査記録なしの状態を付けて実処理する。処理関数後の `operation.succeeded` 等の記録に失敗した場合は、既に処理した操作を再実行させる一般エラーへ変換せず、適用済み結果または終了未確認などの実状態に警告を添えて返す。作業一覧更新は入力検証後、起動中状態を一度に置換するため、更新後の監査失敗時は更新済み成功として返す。操作結果自体が確定できない時は `applied: unknown` と警告を返し、自動再試行を促す成功・失敗扱いをしない。`audit_warning` の応答形式は API 設計で確定する。

実装方式の候補は、共通受付に固定例外 `allowlist` と監査失敗規則を持たせる方法（推奨）と、固定例外専用の別受付を設ける方法である。いずれも任意の `tool` 名、引数、呼出し元申告で例外を広げない。共通受付方式では、例外の `pre-handler` `operation.received/started` と `post-handler` `operation.succeeded/failed` の各失敗点を捕捉して警告状態を維持する。別受付方式では通常受付との認証・所有権・緊急停止確認の重複を避け、同じ固定規則を共有する。

この案では監査欠落を許して安全操作を継続するため、監査内容の完全性は保証しない。通常操作は期限制御の許可判断記録を書ける状態へ監査が復旧するまで停止する。例外操作は監査復旧後に警告を解消するが、直前処理を暗黙に再実行しない。`UI` は監査記録が利用できない状態と、強制中の通常操作が拒否される状態を示す。警告項目の応答形式と監査記録なし状態の画面表現は API 応答契約と合わせて確定する。

### 実行中プロセスの確認と例外境界

現行の `process_start` は所有者とセッションを含む処理 ID を発行し、監視処理が250ms間隔で状態と出力を観測する。自然終了の確認には `completionPending`、出力排出には `outputDrained`、強制停止後には `terminating` と `terminationUnconfirmed` を使う。`process_status` と `process_output` は現在、状態確認時にも Desktop Commander から出力を取得する。`process_kill` は現在 `running` 状態の処理だけを受け付けるため、強制停止が未確認の `terminating` 状態を同じ操作で再試行できない。

当初案の「終了確認待ちだけ `process_status` を許可」では、`running` 状態の処理終了確認を呼出し元から始められず、`process_kill` の時間切れ後に停止を再試行できない。この点は例外が狭すぎるため、次の変更を推奨する。

- `process_status` は同じ使用者が同じセッション内で所有する記録済み処理に限り、強制中も許可する。ただし期限超過の判定後は監視処理が最後に観測した状態だけを返し、追加の Desktop Commander 呼出しや出力取得を起こさない。これで実行中・終了中・終了済みの確認を、許可された読み取りだけで循環せず行える。
- `process_output` は同じ所有確認を必須とする。強制中は保存済みの出力だけ返し、新たな出力取得を下流へ委譲しない。
- `process_kill` は所有者とセッションが一致し、`running` または `terminating` である時だけ通す。`terminating` の再要求は 2 秒以上経過し、終了未確認の場合だけ許可する。同時要求を `processLock` で直列化し、終了済みには停止を再送しない。
- 終了確認と必要な出力排出は既存の監視処理に継続させる。再開後の通常観測は作業一覧を更新してから再実行させる。

代替は `process_status/output` を `terminating`、`completionPending`、`outputDrained` の時だけ許可する方法だが、利用者が停止確認を開始できない実行中状態と、自然終了確認の競合が残る。安全境界は自由な操作名や引数ではなく、既存の処理記録の ID、同じセッションの所有確認、監視処理の保存済み状態だけで制約する。

## 実装前の確認事項

- 利用者が決定したセッション単位・初期有効・有効化後5分猶予と、作業一覧更新・安全停止・終了整理の例外が設計全体で一貫しているか独立して確認する。
- 例外操作の実在 API 名と終了確認条件を現行実装から照合する。
- 永続化先、複数更新の原子性、時計異常の検知方法、監査記録の操作名を実装面と照合する。
- 設計確認後、受入条件に沿った失敗テストを先に追加して、利用者指定のテスト駆動開発に入る。

### 画面確認用の配置案

セッション詳細画面の「セッションの内容」欄より上に、次の順で作業一覧枠を置く。

1. 見出し「作業一覧」と、強制機能の状態および切替操作
2. 未完了件数・完了件数、最終更新時刻
3. 未完了項目を上に並べた項目一覧。各項目に状態変更、編集、削除を配置
4. 作業追加欄と保存操作
5. 期限超過時は拒否理由、最後の更新時刻、ここで更新して再試行する案内

画面の制御は案内に限り、MCP の通常操作を許可する判定はサーバーだけが行う。強制機能の表示は状態と切替導線に限り、期限を利用者端末の時計だけで確定しない。
