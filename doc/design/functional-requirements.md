# 機能要件

## 目的

RemoteDesktopMCP は、あらかじめ許可した1人のユーザーが、リモートから対象PCのファイル操作とプロセス操作を行うための MCP サーバーとする。
ファイル操作とプロセス操作そのものは再実装せず、各実行ノードで `@wonderwhy-er/desktop-commander` が提供する MCP ツールを呼び出す。
初期版では必要最小限の機能に限定する。

## 認証

- OAuth/OIDC によりリモート接続ユーザーを認証する。
- あらかじめ登録された1ユーザーだけアクセスを許可する。
- 登録ユーザー以外からのアクセスは拒否する。
- 許可ユーザーの設定は、対象PC上のローカル操作からだけ変更できるようにする。
- MCP ツールから許可ユーザーを変更する機能は提供しない。

## セッション管理

- RemoteDesktopMCP のセッションは、MCP の通信セッションや HTTP 接続とは別に管理する。
- 認証済みユーザーが `session_open` を実行したとき、暗号学的乱数を使って一意な `session_id` を生成する。
- ファイル操作とプロセス操作では、有効な `session_id` を必須とする。HTTP 接続、接続元、アクセストークンからセッションを自動判定しない。
- 同じ `session_id` は別の HTTP 接続からも継続利用できる。ただし、現在認証されているユーザーが一致する場合だけ受け付ける。
- 各セッションには、作成時刻、最終操作時刻、有効期限、状態を保持する。
- 有効なセッションで操作を受け付けた時点で最終操作時刻を更新し、最後の操作から24時間で期限切れにする。
- `session_close` で明示的に終了できる。終了済み、期限切れ、またはサーバー再起動前の `session_id` は再利用しない。
- `session_list` は有効なセッションだけを一覧表示し、`session_id`、作成時刻、最終操作時刻、有効期限を返す。
- 起動したプロセスは、起動時の `session_id` と関連付けて監査ログへ記録する。セッションが終了または期限切れになっても、それだけを理由にプロセスは自動停止しない。同じユーザーの別の有効なセッションから論理プロセスIDを指定して、状態確認、出力取得、停止を行えるようにする。

## Desktop Commander の利用方針

- 各実行ノードは、ローカルの `@wonderwhy-er/desktop-commander` を `stdio` MCP サーバーとして起動または接続し、実際のファイル操作とプロセス操作はその MCP ツールに実行させる。
- 起動時に `listTools()` で利用可能なツールと入力定義を確認し、実行時は `callTool()` を使って呼び出す。
- RemoteDesktopMCP が公開する `file_*` と `process_*` は、ユーザーの認可、`session_id`、`node_id`、監査、各PCの操作制限を確認したうえで、対応する Desktop Commander ツールを呼び出す。
- RemoteDesktopMCP 自身では、同等のファイル探索、ファイル読み書き、部分編集、プロセス起動、出力取得、停止処理を実装しない。
- RemoteDesktopMCP は、外部ユーザーの認証・認可、セッション管理、ノード間認証、リクエストの振り分け、監査、外部公開するツールと引数の制限、複数PC間で一意なIDの管理を担当する。
- Desktop Commander の管理用ツールや、初期版で許可していないツールは外部 MCP へ公開しない。
- 必須の Desktop Commander ツールがない場合、その操作は利用できないものとし、RemoteDesktopMCP の独自実装へ自動的に切り替えない。
- Desktop Commander 側の設定と RemoteDesktopMCP 側の操作制限の両方を満たすリクエストだけを実行する。RemoteDesktopMCP から Desktop Commander のローカル設定を変更する機能は提供しない。
- 将来、Desktop Commander で提供されないローカル操作を追加する場合は、独自実装が必要な理由と責任範囲を設計書へ明記し、既存ツールで代替できないことを確認してから実装する。

## ファイル操作

- ファイル名およびパスからファイルを検索できること。
- ファイル内容から文字列を検索できること。
- テキストファイルの内容を読み取れること。
- ファイルへ部分的な変更（パッチ）を適用できること。

初期版で公開するツール:

- `file_search`
- `content_search`
- `file_read`
- `file_patch`

## プロセス操作

- コマンドまたはプログラムを起動できること。
- 起動したプロセスの実行状態を取得できること。
- 起動したプロセスの出力を、Desktop Commander が保持する1つの統合出力として取得できること。初期版では stdout と stderr を別々には返さず、Desktop Commander から判別できない区分を推測して付けないこと。
- 起動したプロセスを停止できること。
- プロセスの終了コードを取得できること。

初期版で公開するツール:

- `process_start`
- `process_status`
- `process_output`
- `process_kill`

## ログ

- MCP 経由で行われた操作を記録すること。
- 認証成功および認証拒否を記録すること。
- セッションの開始と、そのセッションで行われた操作を記録すること。
- プロセス起動時にコマンド、PID、セッションを記録すること。
- プロセス終了時に終了結果を記録すること。
- 操作の成功・拒否・失敗を記録すること。
- 監査ログの取得やログ設定の変更は MCP ツールとして公開しない。

## セッション用ツール

初期版で公開するツール:

- `session_open`
- `session_list`
- `session_close`

## 複数 PC 接続

- 1つの ChatGPT 接続から複数の PC を操作できること。
- 外部へ公開する MCP 接続先は統括ノード1台に集約すること。
- 実行ノードは複数台登録できること。
- 統括ノード自身も実行ノードを兼任できること。
- 各実行ノードは一意な `node_id` を持つこと。
- ファイル操作とプロセス操作は対象 `node_id` を指定できること。
- 構成に登録された実行ノードが2台以上ある場合は、接続状態にかかわらずファイル操作とプロセス操作で `node_id` を必須とすること。`node_id` がない場合に接続中のノードを自動選択しないこと。
- ノード登録とノード認証設定は各 PC のローカル操作からだけ変更できること。
- 遠隔実行ノードは外部公開せず、tailnet 内の通信経路で統括ノードと接続すること。
- ノード間通信は Tailscale IP だけで待ち受け、LAN IP やグローバル IP では待ち受けないこと。
- 統括ノードと実行ノードの双方で監査ログを残せること。

初期版で公開するノード管理ツール:

- `node_list`

詳細は `multi-pc-architecture.md` を参照する。

## 初期版の対象外

認証設定と許可ユーザー設定は MCP ツールとして公開しない。

## 公開経路

- 外部公開には Tailscale Funnel を使用する。
- 固定グローバル IP を前提としない。
- ルーター／モデムのポートフォワーディングを必要としない。
- 外部 MCP サーバーはループバック (`127.0.0.1`) だけで待ち受ける。
- 外部クライアントは Tailscale Funnel が提供する HTTPS URL から接続する。
- Funnel 自体を認証手段として使わず、RemoteDesktopMCP 自身がすべての MCP リクエストを認証・認可する。
- Funnel の設定変更機能は MCP ツールとして公開しない。

詳細は `tailscale-funnel-architecture.md` を参照する。
