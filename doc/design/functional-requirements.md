# 機能要件

## 目的

RemoteDesktopMCP は、あらかじめ許可した1人のユーザーが、リモートから対象PCのファイル操作とプロセス操作を行うための MCP サーバーとする。
ファイル操作とプロセス操作そのものは再実装せず、各実行ノードで `@wonderwhy-er/desktop-commander` が提供する MCP ツールを呼び出す。
初期版では必要最小限の機能に限定する。

最初の稼働可能な段階は、1台のPCが統括ノードと実行ノードを兼任するローカル構成である。
この段階では既存のパスワード認証を開発用に利用し、Tailscale Funnel からの公開は行わない。
次に Google OIDC を含む公開認証を実装し、ChatGPT からこの1台のPCを操作する。
複数PC接続は、その後に実装する初期版全体の要件として残す。

## 認証

- OAuth/OIDC によりリモート接続ユーザーを認証する。
- あらかじめ登録された1ユーザーだけアクセスを許可する。
- 登録ユーザー以外からのアクセスは拒否する。
- 許可ユーザー設定は対象PC上のローカル設定として管理する。
- 許可ユーザー設定を変更する専用の MCP ツールや HTTP API は提供しない。
- `process_start` は任意コマンドを OS ユーザー権限で実行できるため、その OS ユーザーが設定ファイルを書き換えられる場合は、許可ユーザーもコマンド経由で同じ操作が可能である。

## セッション管理

RemoteDesktopMCP のセッションは、同じユーザーが行う一連の操作を管理するためのものである。
MCP の通信セッションや HTTP 接続とは別に管理する。

### 開始と継続

認証済みユーザーは、存在する作業ディレクトリの絶対パスと、そのセッションの用途を指定して `session_open` を実行する。
`node_list` はセッション作成前に対象ノードを発見するための認証済み読み取りツールとし、`session_id` を必須にしない。互換のため `session_id` を受け付ける場合も、そのIDは有効性と所有者だけを確認し、一覧の対象ノード選択や絞り込みには使わない。
複数PC設定では対象 `node_id` も解決し、セッションを1台の実行ノードへ固定する。`node_id` の必須判定には、実行ノードを兼任する統括ノード自身と登録済み遠隔実行ノードを合計した台数を使う。合計2台以上なら `session_open` でも `node_id` を必須とし、1台だけなら省略時にその1台を選択する。
作業ディレクトリが存在することは対象ノード上で確認する。遠隔ノードが切断中など、対象ノード上で確認できない場合はセッションを作成しない。
用途と作業ディレクトリを必須とし、暗号学的乱数を使って一意な `session_id` を生成する。
`process_start` で起動するコマンドは、そのセッションに固定したノード上の作業ディレクトリから開始する。
作業ディレクトリは開始位置であり、そこ以外へのアクセスを新たに制限するものではない。
ファイル操作とプロセス操作では、この有効な `session_id` を必ず指定する。呼び出し側が `node_id` を指定する操作では、セッションに固定した `node_id` と一致しなければ拒否する。
HTTP 接続、接続元、アクセストークンからセッションを自動判定しない。

認証済みユーザーが同じで有効期限内なら、別の HTTP 接続からも同じ `session_id` を継続利用できる。
`session_list` は有効なセッションだけを返す。
各セッションには、`session_id`、対象 `node_id`、作業ディレクトリ、用途、作成時刻、最終操作時刻、有効期限、状態を保持する。
一覧では、このうち `session_id`、対象 `node_id`、作業ディレクトリ、用途、作成時刻、最終操作時刻、有効期限を返す。
使用者の画面の有効な接続一覧にも、対象 `node_id`、作業ディレクトリ、用途を表示する。

### 有効期限と終了

有効なセッションで操作を受け付けるたびに、最終操作時刻を更新する。
最後に操作を受け付けてから24時間経過すると、そのセッションは期限切れになる。
`session_close` による明示的な終了も可能とする。
終了済み、期限切れ、またはサーバー再起動前の `session_id` は再利用しない。

### 起動したプロセスとの関係

プロセスを起動したら、起動時の `session_id` と関連付けて監査ログへ記録する。
セッションが終了または期限切れになっても、それだけを理由にプロセスを自動停止しない。
状態確認、出力取得、停止には、起動時と同じ有効な `session_id` が必要である。
別のセッションからは、そのプロセスの論理IDを指定しても操作できない。

## Desktop Commander の利用方針

### RemoteDesktopMCP と Desktop Commander の分担

RemoteDesktopMCP は、ユーザーの認証・認可、セッション管理、ノード間認証、操作対象の選択、監査を担当する。
外部公開するツールと引数を制限し、複数PC間で一意なIDも管理する。

実際のファイル操作とプロセス操作は、各PC上の Desktop Commander が担当する。
RemoteDesktopMCP 側で同じファイル探索、読み書き、部分編集、プロセス起動、出力取得、停止処理を重複して実装しない。

### 呼び出しの流れ

1. 各実行ノードで `@wonderwhy-er/desktop-commander` を `stdio` MCP サーバーとして起動または接続する。
2. 起動時に `listTools()` で利用可能なツールと入力定義を確認する。必須ツールがない操作は利用不可とし、独自実装へ切り替えない。
3. `file_*` または `process_*` のリクエストを受けたら、ユーザーの認可、`session_id`、`node_id`、監査、各PCの操作制限を確認する。
4. 確認が済んだら、対応する Desktop Commander ツールを `callTool()` で呼び出す。

### 公開範囲と設定の制限

Desktop Commander 側の設定と RemoteDesktopMCP 側の操作制限の両方を満たすリクエストだけを実行する。
Desktop Commander の管理用ツールや、初期版で許可していないツールは外部へ公開しない。
RemoteDesktopMCP から Desktop Commander の設定を変更する専用機能も提供しない。

固定版 Desktop Commander を RemoteDesktopMCP から起動する場合は、専用の Desktop Commander 設定ファイルを `DATA_DIR` 配下に保持する。通常ユーザーの `~/.claude-server-commander/config.json` は参照・変更しない。
設定パスの分離は RemoteDesktopMCP 側の専用起動処理で行い、ユーザー固有の環境変数を別ディレクトリ向けに差し替える方法は使わない。
設定ファイルの親ディレクトリと、RemoteDesktopMCP および Desktop Commander の
検索許可ディレクトリが、実体パスで親子関係にある構成は起動時に拒否する。
設定ファイルを検索させた後で結果だけを隠す方式は認めない。
`file_search`、`content_search`、`file_read`、`file_patch`、`file_transfer_*` では、
設定ファイルの実体を検索結果、読み取り対象、変更対象、転送元、転送先に含めない。
検索以外の操作でも、許可ディレクトリ内に見える設定ファイルへの直接指定は拒否する。
ファイル操作は設定済みの許可ディレクトリを基準とし、セッションの作業ディレクトリへ暗黙に切り替えない。
`node_list` で基準の絶対パスを返し、転送開始・確定の応答でも実際の対象パスを確認できること。

この除外は RemoteDesktopMCP のファイル操作 API に対する保護である。
`process_start` は同じ OS ユーザー権限で任意コマンドを実行できるため、
コマンド経由の設定ファイルアクセスまで隔離するものではない。
初期版では、そのための追加の実行隔離機構や別 OS ユーザーを必須にしない。

将来、Desktop Commander にないローカル操作が必要になった場合は、既存ツールで代替できないことを確認する。
そのうえで、独自実装が必要な理由と責任範囲を設計書へ明記してから実装する。

### プロセス実行の権限モデル

初期版では、Desktop Commander と `process_start` から起動するプロセスを、
RemoteDesktopMCP を起動した OS ユーザーと同じ権限で実行してよい。

Desktop Commander は RemoteDesktopMCP 起動時のユーザー環境をそのまま継承する。`USERPROFILE`、`APPDATA`、`LOCALAPPDATA`、`HOME`、`HOMEDRIVE`、`HOMEPATH` などのユーザー固有の環境変数は、値だけでなく未設定状態も含めて上書き・合成しない。`process_start` から起動する子プロセスも同じ環境を継承する。

RemoteDesktopMCP 固有の監査ログ、一時ファイル、転送状態、専用 Desktop Commander 設定などは `DATA_DIR` 配下へ分離する。分離のために `HOME` などを別ディレクトリ向けに差し替えたり、特定 CLI 専用の環境変数を追加したりしない。同じ OS ユーザーが通常のローカル実行で CLI 設定や認証状態を更新した場合、新しく起動する `process_start` は RemoteDesktopMCP の再起動なしで同じユーザー環境の状態を参照できること。

認証済みの許可ユーザーは、`process_start` を通して
その OS ユーザーが実行できるコマンドやアクセスできるファイルを操作できるものとして扱う。
これは初期版で意図した権限モデルであり、RemoteDesktopMCP は任意コマンドに対する
追加の実行隔離機構を提供しない。

`file_search`、`content_search`、`file_read`、`file_patch` の
許可ディレクトリは、それらのファイル操作ツールの操作範囲を制限するための設定である。
`process_start` から起動した任意コマンドのファイルアクセスを制限するものではない。

そのため、RemoteDesktopMCP を起動する OS ユーザーが読み書きできる設定やファイルは、
`process_start` から起動したコマンドからも到達できる可能性がある。
この権限を許可ユーザーへ与えられない環境では、運用者が RemoteDesktopMCP 自体を
より権限の小さい OS ユーザーで起動する。

別 OS ユーザー、OS のアクセス権による追加隔離などを導入してもよいが、
初期版の必須条件にはしない。
追加隔離を導入していないことだけを理由に `process_start` を利用不可にはしない。

## ファイル操作

- ファイル名およびパスからファイルを検索できること。
- ファイル内容から文字列を検索できること。
- テキストファイルの内容を読み取れること。
- ファイルへ部分的な変更（パッチ）を適用できること。

初期版で公開するツール:

- `file_search`
- `content_search`
- `file_read`
- `file_patch`

## ファイル転送

RemoteDesktopMCP は、ChatGPT と対象PCの間でファイルを双方向に転送できること。
Desktop Commander 自体には汎用バイナリ転送を追加せず、転送は RemoteDesktopMCP の機能として提供する。

初期版では、既存の MCP 接続上でファイル本体を分割して送受信する。
外部の一時URLや追加の公開ポートを必須にせず、Tailscale Funnel 経由で確立済みの MCP 接続だけで完結できるようにする。

転送開始時に一意な `transfer_id` を発行し、ファイル名、サイズ、SHA-256、対象 `node_id`、転送方向を管理する。
ファイル本体は一定サイズのチャンクに分割し、MCP ツールの引数または結果では base64 で表現する。

ダウンロードでは、開始時に作成して固定した一時複製からサイズとSHA-256を算出し、全チャンクを同じ複製から読む。
送信した全バイト列のSHA-256が開始時の値と一致した場合だけ完了とする。
アップロードでは、転送先と同じディレクトリの一時ファイルへ書き込み、全チャンク受信後にサイズとSHA-256を確認してから確定する。
上書き不可の場合は、開始後に別の処理が転送先を作成していても、確定時に原子的に既存ファイルを保護して失敗する。
既存ファイルの上書きは明示指定された場合だけ許可する。

ファイル転送でも各実行ノードの許可ディレクトリを適用する。
Desktop Commander のサーバー設定ファイルは転送元・転送先のどちらにも指定できない。

初期版で公開する転送ツール:

- `file_transfer_download_begin`
- `file_transfer_download_chunk`
- `file_transfer_upload_begin`
- `file_transfer_upload_chunk`
- `file_transfer_upload_commit`
- `file_transfer_status`
- `file_transfer_cancel`

## プロセス操作

- コマンドまたはプログラムを起動できること。
- 起動したプロセスの実行状態を取得できること。
- 起動したプロセスの出力を、Desktop Commander が保持する1つの統合出力として取得できること。初期版では stdout と stderr を別々には返さず、Desktop Commander から判別できない区分を推測して付けないこと。
- 起動したプロセスを停止できること。
- プロセスの終了コードを取得できること。

初期版で公開するツール:

- `process_start`
- `process_status`
- `process_output`
- `process_kill`

## ログ

使用者の履歴は画面全体を再読み込みせず取得し、新着通知と本人による反映を分ける。
基準パスの明示と履歴取得の詳細は [ファイル操作の基準パスと使用者ログの更新](file-paths-and-live-logs.md) に従う。

- MCP 経由で行われた操作を記録すること。
- 認証成功および認証拒否を記録すること。
- セッションの開始と、そのセッションで行われた操作を記録すること。
- プロセス起動時にコマンド、PID、セッションを記録すること。
- プロセス終了時に終了結果を記録すること。
- 操作の成功・拒否・失敗を記録すること。
- 監査ログの取得やログ設定の変更は MCP ツールとして公開しない。

### 使用者の実行状態と停止

通常の呼び出し履歴は使用者の画面から確認する。使用者は検証済みの認証主体に属する接続と実行だけを閲覧し、自分の実行全体を停止・再開できる。管理者と使用者は独立した権限として扱う。
停止は使用者単位で保存し、サーバー再起動や新規接続によって解除しない。停止以前の接続は世代によって無効化し、明示的な再開後も再利用しない。実行中の操作と関連プロセスを停止対象に含める。
詳細な認可、停止と再開の競合、永続化、停止保証の範囲は [使用者の画面と緊急停止](user-console-emergency-stop.md) を参照する。

### 管理者向け監査情報の表示

管理者画面はサーバー状態と運用・認証に関する監査情報を対象とする。通常のツール呼び出し履歴、コマンド、実行出力は使用者の画面で本人に表示する。
MCP の許可ユーザー設定とは独立して管理者を設定し、`ADMIN_USERS` にメールアドレスまたは Google の `sub` を `,` で区切って登録する。Google OIDC が設定されている場合は Google ログインを使用し、それ以外ではローカルのメールアドレスとパスワードでログインする。
管理者セッションは専用の認証情報で管理し、有効期間は1時間とする。Google 公開認証側の許可状態は各リクエストで再確認する。ログイン試行にはレート制限を適用する。
ログインとログイン終了の送信要求は `BASE_URL` と完全一致する送信元のみ受け付ける。管理画面は認証必須とし、応答を保存させない。ログイン終了ではサーバー側の状態を破棄する。

### 画面の受け入れ条件

- 未認証の画面要求はログイン画面へ転送する。
- 管理者権限だけで使用者の操作履歴や停止・再開操作にアクセスできない。
- 使用者の履歴は本人だけに限定し、他の使用者の接続や操作識別子を指定しても情報を返さない。
- 使用者の画面に受信・開始・終了時刻、所要時間、接続と操作の識別子、ツール名、対象概要、実行状態を表示する。
- コマンドと出力に含まれる既知の秘密情報を秘匿し、保存・表示件数の上限を明示する。対応条件外の秘密情報をすべて検出する保証はない。
- 明示的な停止後は再接続しても実行を拒否し、再起動後も停止を維持する。再開後も古い接続を復活させない。

## 複数 PC 接続

- 1つの ChatGPT 接続から複数の PC を操作できること。
- 外部へ公開する MCP 接続先は統括ノード1台に集約すること。
- 実行ノードは複数台登録でき、統括ノード自身も実行ノードを兼任できること。
- 複数PC設定ファイルがない既存環境は単一PC互換モードで従来の `LOCAL_NODE_ID` と `LOCAL_NODE_LABEL` を使用し、複数PC設定を初期化した後だけ設定ファイルを正とすること。
- 複数PC設定モードの各ノードは再起動後も変わらない暗号学的乱数由来の一意な `node_id` と表示名をローカル設定に保持すること。端末名やIPアドレスから `node_id` を導出しないこと。
- 遠隔実行ノードは Tailscale Funnel や受信用ポートを公開せず、tailnet 内から実行ノード側で統括ノードへの持続接続を開始すること。
- 統括ノードのノード間通信は Tailscale IPv4 だけで待ち受け、`0.0.0.0`、LAN IP、グローバル IP では待ち受けないこと。
- ノード間通信は長さ付きフレームに上限を設け、未認証・不正形式・上限超過の入力を操作処理へ渡さないこと。
- 統括ノードと実行ノードの組ごとに異なる32バイトPSKを使用し、nonce、HMAC-SHA-256、HKDF-SHA-256 による相互認証と各フレームの完全性・再送防止を行うこと。
- 同じ `node_id` では操作可能な `active` 接続を1本だけ保持すること。置換候補を同期中は旧 `active` 接続を維持し、候補の同期成功時だけ原子的に入れ替えること。同期に失敗した候補だけを閉じ、旧接続の応答を新しい接続の要求結果として採用しないこと。
- 生存確認で切断を検出し、実行ノードは同じ `node_id` で再接続すること。統括ノードとの通信だけの再接続では実行ノード世代と Desktop Commander の世代を変更せず、実行ノードの RemoteDesktopMCP プロセスの再起動は新しい実行ノード世代として識別すること。
- 遠隔の転送資源とプロセス資源は実行ノード側の非公開IDと所有情報を正とし、統括ノードが外部へ返すIDは対象 `node_id`、実行ノード世代、実行ノード内IDへの対応として管理すること。統括ノードから任意の PID や Desktop Commander ツール名を指定して実行させないこと。
- 公開 MCP のローカル実行経路と実行ノードの遠隔要求処理は、同じ固定内部操作の契約表と共通実行処理を使用すること。内部操作の操作区分、入力形式、応答形式、監査種別、セッション必須有無を1か所で定義し、ノード間通信層へファイル操作、転送、プロセス操作の状態遷移を重複実装しないこと。
- RemoteDesktopMCP の各セッションは対象実行ノード1台へ固定し、そのノード上の作業ディレクトリを保持すること。別ノードの操作へ同じ `session_id` を流用しないこと。
- 使用者の停止状態は統括ノードを正とし、停止世代と検証済み主体を遠隔実行ノードへ同期すること。遠隔要求は同期済みの停止世代と一致するときだけ実行し、停止中、未同期、古い世代の要求を実行しないこと。
- ファイル操作、ファイル転送、プロセス操作は対象 `node_id` を指定できること。
- 操作対象となる実行ノードが、実行ノードを兼任する統括ノード自身と登録済み遠隔実行ノードを合計して2台以上ある場合は、接続状態にかかわらずファイル操作、ファイル転送開始、プロセス操作で `node_id` を必須とすること。`node_id` がない場合に接続中のノードを自動選択しないこと。
- 指定したノードが未登録、切断中、対象操作を利用不可、または混雑中の場合、別ノードへ自動的に振り替えないこと。
- 送信済み要求の完了を切断・接続交代・応答期限超過によって確認できない場合、成功を推測せず結果不明として返すこと。副作用を持つ要求を自動再送しないこと。
- 遠隔ダウンロードのチャンク応答は、固定済み読み取り用複製から得た直前の同一 `offset` の応答を実行ノードが保持し、応答喪失後の同一 `offset` 再要求へ同じデータ、次の位置、完了有無を返せること。再送では転送位置とSHA-256計算を進めず、最終チャンクも完了後に再送できること。
- ノード登録、削除、PSK更新、統括ノード接続先の設定と解除はローカル CLI とローカル設定から行い、ノード管理用 MCP ツール、公開 HTTP 管理 API、自動参加機能を追加しないこと。
- 実行ノードで統括ノード接続先を解除した場合は、接続先とPSKを同じ設定更新で削除し、現在の接続を閉じて再接続を開始しないこと。
- ノード構成の更新は完全な設定単位で検証・適用し、不正設定を部分適用しないこと。登録解除またはPSK更新時は対象の既存接続を切断すること。登録解除時は対象ノードへ固定された既存セッションも終了し、そのノードの公開転送IDと公開論理プロセスIDを別ノードや後の再登録へ引き継がないこと。
- `node_list` は認証済みユーザーが `session_open` より前に呼び出せる読み取りツールとし、登録済み実行ノードを切断中も含めて返し、現在接続で確認した接続状態、利用可能な操作、ファイルルート、最終確認時刻を示すこと。`session_id` を対象ノードの選択条件にしないこと。
- 統括ノードと実行ノードの双方で、共通の `request_id` と対象 `node_id`、遠隔ノード間通信ではさらに `connection_id` により操作を追跡できる監査ログを残し、PSK、nonce、HMAC値、セッション鍵を記録しないこと。
- PC追加、PSK更新、登録解除の利用者手順を実装時に `doc/remote-setup.md` へ反映すること。

初期版で公開するノード管理ツール:

- `node_list`

`node_list` 以外の登録・設定変更ツールは MCP として公開しない。
詳細は `multi-pc-architecture.md` を参照する。

## 初期版の対象外

認証設定と許可ユーザー設定は MCP ツールとして公開しない。

## 公開経路

- 外部公開には Tailscale Funnel を使用する。
- 固定グローバル IP を前提としない。
- ルーター／モデムのポートフォワーディングを必要としない。
- 外部 MCP サーバーはループバック (`127.0.0.1`) だけで待ち受ける。
- 外部クライアントは Tailscale Funnel が提供する HTTPS URL から接続する。
- Funnel 自体を認証手段として使わず、RemoteDesktopMCP 自身がすべての MCP リクエストを認証・認可する。
- Funnel の設定変更機能は MCP ツールとして公開しない。

詳細は `tailscale-funnel-architecture.md` を参照する。
