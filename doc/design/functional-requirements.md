# 機能要件

## 目的

RemoteDesktopMCP は、あらかじめ許可した1人のユーザーが、リモートから対象PCのファイル操作とプロセス操作を行うための MCP サーバーとする。
ファイル操作とプロセス操作そのものは再実装せず、各実行ノードで `@wonderwhy-er/desktop-commander` が提供する MCP ツールを呼び出す。
初期版では必要最小限の機能に限定する。

## 認証

- OAuth/OIDC によりリモート接続ユーザーを認証する。
- あらかじめ登録された1ユーザーだけアクセスを許可する。
- 登録ユーザー以外からのアクセスは拒否する。
- 許可ユーザーの設定は、対象PC上のローカル操作からだけ変更できるようにする。
- MCP ツールから許可ユーザーを変更する機能は提供しない。

## セッション管理

RemoteDesktopMCP のセッションは、同じユーザーが行う一連の操作を管理するためのものである。
MCP の通信セッションや HTTP 接続とは別に管理する。

### 開始と継続

認証済みユーザーが `session_open` を実行すると、暗号学的乱数を使って一意な `session_id` を生成する。
ファイル操作とプロセス操作では、この有効な `session_id` を必ず指定する。
HTTP 接続、接続元、アクセストークンからセッションを自動判定しない。

認証済みユーザーが同じで有効期限内なら、別の HTTP 接続からも同じ `session_id` を継続利用できる。
`session_list` は有効なセッションだけを返す。
各セッションには、`session_id`、作成時刻、最終操作時刻、有効期限、状態を保持する。
一覧では、このうち `session_id`、作成時刻、最終操作時刻、有効期限を返す。

### 有効期限と終了

有効なセッションで操作を受け付けるたびに、最終操作時刻を更新する。
最後に操作を受け付けてから24時間経過すると、そのセッションは期限切れになる。
`session_close` による明示的な終了も可能とする。
終了済み、期限切れ、またはサーバー再起動前の `session_id` は再利用しない。

### 起動したプロセスとの関係

プロセスを起動したら、起動時の `session_id` と関連付けて監査ログへ記録する。
セッションが終了または期限切れになっても、それだけを理由にプロセスを自動停止しない。
同じユーザーが別の有効なセッションを開けば、論理プロセスIDを指定して状態確認、出力取得、停止を行える。

## Desktop Commander の利用方針

### RemoteDesktopMCP と Desktop Commander の分担

RemoteDesktopMCP は、ユーザーの認証・認可、セッション管理、ノード間認証、操作対象の選択、監査を担当する。
外部公開するツールと引数を制限し、複数PC間で一意なIDも管理する。

実際のファイル操作とプロセス操作は、各PC上の Desktop Commander が担当する。
RemoteDesktopMCP 側で同じファイル探索、読み書き、部分編集、プロセス起動、出力取得、停止処理を重複して実装しない。

### 呼び出しの流れ

1. 各実行ノードで `@wonderwhy-er/desktop-commander` を `stdio` MCP サーバーとして起動または接続する。
2. 起動時に `listTools()` で利用可能なツールと入力定義を確認する。必須ツールがない操作は利用不可とし、独自実装へ切り替えない。
3. `file_*` または `process_*` のリクエストを受けたら、ユーザーの認可、`session_id`、`node_id`、監査、各PCの操作制限を確認する。
4. 確認が済んだら、対応する Desktop Commander ツールを `callTool()` で呼び出す。

### 公開範囲と設定の制限

Desktop Commander 側の設定と RemoteDesktopMCP 側の操作制限の両方を満たすリクエストだけを実行する。
Desktop Commander の管理用ツールや、初期版で許可していないツールは外部へ公開しない。
RemoteDesktopMCP から Desktop Commander のローカル設定を変更する機能も提供しない。

将来、Desktop Commander にないローカル操作が必要になった場合は、既存ツールで代替できないことを確認する。
そのうえで、独自実装が必要な理由と責任範囲を設計書へ明記してから実装する。

### ローカル実行の権限分離

RemoteDesktopMCP の認証設定やノード認証情報を管理するプロセスと、Desktop Commander およびそこから起動するコマンドは、別の OS ユーザーで実行する。
初期版では、Desktop Commander 側を管理者権限を持たない専用ユーザーで動かし、コマンドとその子孫プロセスにも同じ制限を適用する。

専用ユーザーには、ファイル操作やコマンド実行を許可する作業用ディレクトリだけを OS のアクセス権で許可する。
次の情報や設定には、専用ユーザーから読み書きできない OS アクセス権を設定する。

- 許可ユーザー設定
- OAuth/OIDC の秘密情報と保存済みトークン
- ノード登録情報、PSK、ノード認証設定
- 監査ログ
- RemoteDesktopMCP の `DATA_DIR`
- 実行ユーザー、許可ディレクトリ、起動方法など、この権限境界を決める設定
- RemoteDesktopMCP と実行用プロセスのサービス設定、起動スクリプト、実行ファイルなど、境界を変更できるファイル

Desktop Commander の `allowedDirectories` は追加の制限として利用するが、`process_start` の保護境界としては扱わない。
シェル、インタープリター、リダイレクト、子孫プロセスを使っても、OS のアクセス権で保護した領域へ到達できないことを前提とする。

RemoteDesktopMCP 本体の環境変数を Desktop Commander や起動コマンドへそのまま継承しない。
実行側へ渡す環境変数は安全な値だけを明示的に構成し、OAuth/OIDC の秘密情報、トークン、PSK などを含めない。
管理用の通信ハンドルもコマンドや子孫プロセスへ継承させない。

統括ノード自身を実行ノードとして使う場合も、この権限分離を省略しない。
必要な専用ユーザー、OS のアクセス権、実行経路を用意できない場合は `process_start` を利用不可とし、同じ OS ユーザーでの無制限なコマンド実行へ切り替えない。

## ファイル操作

- ファイル名およびパスからファイルを検索できること。
- ファイル内容から文字列を検索できること。
- テキストファイルの内容を読み取れること。
- ファイルへ部分的な変更（パッチ）を適用できること。

初期版で公開するツール:

- `file_search`
- `content_search`
- `file_read`
- `file_patch`

## プロセス操作

- コマンドまたはプログラムを起動できること。
- 起動したプロセスの実行状態を取得できること。
- 起動したプロセスの出力を、Desktop Commander が保持する1つの統合出力として取得できること。初期版では stdout と stderr を別々には返さず、Desktop Commander から判別できない区分を推測して付けないこと。
- 起動したプロセスを停止できること。
- プロセスの終了コードを取得できること。

初期版で公開するツール:

- `process_start`
- `process_status`
- `process_output`
- `process_kill`

## ログ

- MCP 経由で行われた操作を記録すること。
- 認証成功および認証拒否を記録すること。
- セッションの開始と、そのセッションで行われた操作を記録すること。
- プロセス起動時にコマンド、PID、セッションを記録すること。
- プロセス終了時に終了結果を記録すること。
- 操作の成功・拒否・失敗を記録すること。
- 監査ログの取得やログ設定の変更は MCP ツールとして公開しない。

## セッション用ツール

初期版で公開するツール:

- `session_open`
- `session_list`
- `session_close`

## 複数 PC 接続

- 1つの ChatGPT 接続から複数の PC を操作できること。
- 外部へ公開する MCP 接続先は統括ノード1台に集約すること。
- 実行ノードは複数台登録できること。
- 統括ノード自身も実行ノードを兼任できること。
- 各実行ノードは一意な `node_id` を持つこと。
- ファイル操作とプロセス操作は対象 `node_id` を指定できること。
- 構成に登録された実行ノードが2台以上ある場合は、接続状態にかかわらずファイル操作とプロセス操作で `node_id` を必須とすること。`node_id` がない場合に接続中のノードを自動選択しないこと。
- ノード登録とノード認証設定は各 PC のローカル操作からだけ変更できること。
- 遠隔実行ノードは外部公開せず、tailnet 内の通信経路で統括ノードと接続すること。
- ノード間通信は Tailscale IP だけで待ち受け、LAN IP やグローバル IP では待ち受けないこと。
- 統括ノードと実行ノードの双方で監査ログを残せること。

初期版で公開するノード管理ツール:

- `node_list`

詳細は `multi-pc-architecture.md` を参照する。

## 初期版の対象外

認証設定と許可ユーザー設定は MCP ツールとして公開しない。

## 公開経路

- 外部公開には Tailscale Funnel を使用する。
- 固定グローバル IP を前提としない。
- ルーター／モデムのポートフォワーディングを必要としない。
- 外部 MCP サーバーはループバック (`127.0.0.1`) だけで待ち受ける。
- 外部クライアントは Tailscale Funnel が提供する HTTPS URL から接続する。
- Funnel 自体を認証手段として使わず、RemoteDesktopMCP 自身がすべての MCP リクエストを認証・認可する。
- Funnel の設定変更機能は MCP ツールとして公開しない。

詳細は `tailscale-funnel-architecture.md` を参照する。
