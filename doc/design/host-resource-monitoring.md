# 利用者画面のPC使用状況

## 目的と範囲

課題 #47 に対し、利用者画面 `/user` で、選択したPC全体の使用状況を読み取り専用で示す。操作セッションの詳細画面には追加しない。最初の対象は `FA780` 上で動く RemoteDesktopMCP のPC全体とする。計測結果には対象 `node_id` と表示名を含める。

複数PCでは、選択したノードごとに値を分け、ノード間を合算しない。取得失敗や非対応の場合も選択を切り替えず、そのノードの状態を表示する。選択IDと実際の取得先が一致しない場合は値を返さず、統括PCの値などに置き換えない。

画面には処理装置使用率、メモリ使用量（使用量・総量・割合）、ネットワーク受信量・送信量を対象・単位・観測時刻または測定期間とともに示す。初回取得中、取得失敗、未対応、古い値を区別し、取得間隔を利用者が選べるようにする。

## 値の定義

| 指標 | 取得元と範囲 | 計算・表示 | 制約 |
| --- | --- | --- | --- |
| 処理装置使用率 | 選択PC全体。標準 `node:os` の全論理処理装置の累積時間 | `100 × (全時間差分 − 待機時間差分) ÷ 全時間差分`。全処理装置を分母に含めて 0–100% に正規化し、測定開始・終了時刻と実経過時間も示す | 前回値がない初回、分母0、無効な差分は割合を出さず「測定中」等とする。値は直近の共有標本間の平均であり瞬間値ではない |
| メモリ | 選択PC全体。`node:os` の `totalmem()` と `freemem()` | 総量=`totalmem()`、空き量=`freemem()`、使用量=総量−空き量、割合=100×使用量÷総量。容量は2進単位の `GiB`、小さい値は `MiB` で示す | PC全体の物理メモリであり、プロセス単体の使用量や予約量ではない。取得不可、総量0なら未対応状態とする |
| ネットワーク受信・送信 | 取得元が提供する場合に限り、PC上の機器ごと | OSの累積受信・送信値をバイトで示す。速度は共有標本間の増分÷単調時計で測った実経過秒とし、バイト/秒または適切な2進単位で示す | 機器別の全通信量であり、LANとインターネットを区別しない。「インターネット通信量」と表示しない。機器ごとに示し、合算しない |

壁時計の補正に影響されないよう差分の経過時間には単調時計を使う。画面に示す時刻は利用者向けの観測時刻とする。

## 取得できる範囲と段階

### 第1段階: 処理装置とメモリ

依存追加なしで標準 `node:os` の読取を使う。対象OSで同じ意味の値が得られるか実装時に確認し、例外や欠損は指標別に未対応または取得失敗とする。ネットワーク機器のアドレス一覧は受送信量の代用にしない。

### 第2段階: ネットワーク機器の全受送信量

標準 `node:os` からは機器ごとの累積受送信量を得られない。Windowsの候補は [GetIfEntry2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getifentry2) と [MIB_IF_ROW2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_if_row2) の `InOctets` / `OutOctets`。機器を通る全種類の通信量で、通信先がLANか外部かは分からない。

OSには取得元があっても、現在の実行環境からその構造を読む標準APIはない。追加依存または別のOS読取手段が必要となるため、承認前には実装しない。拒否されたOS読取を繰り返したり、別経路に替えて拒否を迂回したりしない。承認済み取得元がなければネットワーク指標は「未対応」とする。新しい依存、権限、認証情報、OS設定は追加しない。

### インターネット専用量

機器の累積値からLANとインターネットを厳密に分けることはできない。別の取得元を使う場合も、取得範囲の検証と別設計が必要となる。根拠のない分類はしない。

## 機器の重複と値の再設定

- 取得元にある物理、仮想、仮想専用網、自己通信機器等を個別に表示し、種類を識別できない場合は種類不明とする。同じ通信が複数機器に計上されることがある旨を画面に示し、全機器合計を作らない。
- IPアドレス、物理アドレス、内部の安定識別子、利用者名、通信先は応答とログに含めない。表示は識別に必要な機器名または種類に限る。
- 機器の追加・削除、再出現、識別子変更、OS再起動、累積値の減少を新しい基準点として扱い、その時点の速度は `null` とする。負の増分や値の周回を推測した補正を表示しない。
- 累積値はOSが現在報告する値であり、PC起動以来またはサービス稼働以来の合計とは呼ばない。取得値が減少した場合は基準点を更新する。

## 間隔、共有計測、配信

- 既定10秒、選択肢5・10・30・60秒。範囲は5–60秒で、5秒未満や範囲外は受け付けない。
- サーバーはPCごとに共有計測器を1つ置く。有効な利用者の要求間隔のうち最短値を標本間隔とする。前回の読取が終わる前に次を始めない。
- 例えば利用者Aが10秒、Bが30秒なら、共有計測は10秒ごとに1回行い、Aへ10秒ごと、Bへ30秒ごとに同じ最新標本を配信する。Bの更新は速くならず、Aの指定がBの頻度を上書きすることもない。通知値には実際の観測時刻と標本間の測定期間を必ず含める。
- 処理装置の前回累積値と差分計算の基準点は共有計測器だけが保持・更新する。利用者の購読開始、間隔変更、切断では基準点を変更しない。割合は各共有標本で一度だけ算出し、全利用者に同じ結果を配信する。購読者がいない間は取得を止め、次の開始時は新しい基準点から測定中とする。
- 同時通知接続はサーバープロセス全体で最大32。超過時は `503` と `Retry-After` を返す。利用者別に最終配信時刻を持ち、各利用者の指定間隔に達した時だけ配信する。利用者別の時計は配信可否にだけ使い、共有計測の差分基準点に使わない。
- 画面が非表示になればその接続を閉じ、表示に戻れば認証して再接続する。購読者がいない場合は定期取得しない。サーバー側でも間隔を検証する。
- 値には観測時刻を含め、利用者の指定間隔の2倍を超えたら古い値とする。最後の成功値を保持する場合も時刻と古い状態を隠さない。ある指標の失敗で他指標を止めない。

## 選択PC、認証、認可

- `/user` の既存ログイン確認に加え、選択PCがその利用者に許可された対象か確認する。要求された `node_id` と応答の `node_id` を照合し、一致しなければ値を返さない。対象が未接続、未登録、未対応、または失敗の場合も統括PCや別の実行PCへ切り替えない。
- 現在の `src/user-console.ts:213` はログイン利用者の識別子を設定し、`:226` は画面に出すセッションをその利用者の所有物に限定する。しかし利用者画面のログイン確認だけでは、PC全体情報の取得権限やノード別の許可を証明しない。
- 既存の `node_list` は `src/index.ts:1126` で呼出利用者の有効な操作セッションを確認してから利用可能なノードを返す。`:545` の `session(user, sessionId)` は本人所有・有効状態・期限内を確認し、`:546` の `node(nodeId)` は現在のローカルノード以外を拒否する。設計上、複数PCでは利用者が操作できる実行ノードだけを列挙する（`doc/design/multi-pc-architecture.md:570`）。
- その既存権限確認で許可されたノードだけを選択候補とする。一般ログイン利用者にPC全体情報の読取を追加で認める権限は現行コードで確認できないため、ログインだけで全PCを見せない。画面で認可済みノードを解決できないときは閉じ、画面用の追加権限を設けるかは未決事項とする。
- 自動読取、再接続、定期通知は無操作期限を延長しない（[設計変更 #49](https://github.com/ssaattww/RemoteDesktopMCP/pull/49) の方針）。期限延長は利用者の実操作だけで行う。認証期限が切れたら通知を終了する。
- 計測用の認証情報、公開MCP操作、設定変更、コマンド実行、ファイルアクセスは追加しない。権限やOS設定を変えず、拒否された機能を迂回しない。
- 応答は要求・実測のノードID、表示名、取得時刻、単位、指標状態、処理装置の測定期間、メモリの総量・使用量・空き量、取得できる場合だけ機器別累積量と速度に限る。認証情報、利用者名、アドレス、内部識別子、通信先、コマンド、監査本文を含めず、`Cache-Control: no-store` とする。

## 読取経路と画面状態

- 利用者画面 `/user` 専用に、読み取り用 `GET /user/api/host-metrics` と `GET /user/api/host-metrics/events?intervalSeconds=10` を設ける案とする。両方の応答形式は共通にし、要求ごとに許可対象PCを確認する。
- 既存 `/api/events` は監査ログの取得位置、セッション絞り込み、再同期の契約を持つため計測値を混ぜない。既存の同一オリジン認証、`EventSource` 接続管理、応答終了処理を参考に、専用読取経路を作る。
- 最小応答は、要求ノードID・実測ノードID・表示名・観測時刻と、各指標の状態・値・単位を含む。状態は `measuring`、`ok`、`stale`、`unsupported`、`error` を区別し、取得失敗時にOSの詳細を返さない。値は形式例であり実測値ではない。
- 画面は初回を「測定中」、非対応を「未対応」、失敗を再試行付きで示す。前回値は取得時刻と「古い値」を併記し、通知切断中に最新値として見せない。間隔変更では現在の画面状態を保って接続を切り替える。
- 機器名と値はHTMLとして挿入せず、テキストとして表示する。

## 合成値を用いるテスト駆動計画

実機に負荷を作らず、注入する読取器と固定時計を使う。合成値で先に契約テストを作り、その後に実装する。

1. 処理装置の合計時間差分10,000、待機時間差分6,000で40%、測定期間10秒を確認。初回と分母0は割合なし。
2. メモリ総量16 `GiB`、空き10 `GiB` で使用6 `GiB`・37.5%を確認。
3. 承認済みネットワーク取得器を後続実装する場合、別々の2機器を使い、受信1,000バイト/5秒が200バイト/秒となること、機器別表示だけで合計がないことを確認。
4. 10秒指定の利用者と30秒指定の利用者が同時にいる場合、10秒ごとに読取器が1回動き、配信は各10秒・30秒になることを固定時計で確認。配信が速い利用者や購読解除が共有CPU基準点を変えないことも確認。
5. 累積値減少・機器再出現・初回の速度が `null`、値が負にならないことを確認。選択ノードが取得不能または別IDを返した場合、統括PCの値で置き換えないことを確認。
6. 範囲外の間隔拒否、5秒下限、32接続上限、非表示時切断、購読者がいない場合は停止、指標ごとの失敗表示、認証、ノード許可、無操作期限非延長、応答の情報最小化を確認。

## 親の設計判断

1. 厳密なインターネット専用量を必須にするか、機器別の全ネットワーク送受信量を後続機能として受け入れるか。
2. 後続のネットワーク計測で新依存または別の許可済みOS読取手段を認めるか。承認までは処理装置とメモリだけを第1段階とする。
3. 一般利用者にPC情報の読取を許すか。既存の操作可能ノード認可を利用者画面に適用できない場合、追加権限を設けるか。
4. 5/10/30/60秒と同時32接続の上限を初期値として採用するか。
