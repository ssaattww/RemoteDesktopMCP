# ホーム画面のホスト使用状況表示

## 目的と対象

Issue #47 に対し、ホーム画面でホスト全体の使用状況を読み取り専用で表示する。セッション詳細画面には追加しない。最初の対象は `FA780` 上の RemoteDesktopMCP プロセスが動く PC 全体とする。画面とデータには対象ノード名を必ず含める。

複数ノード構成では、選択中のノードごとに値を分けて表示する。統括ノードを選んだ場合は統括ノード自身の PC、実行ノードを選んだ場合はその実行ノード自身の PC を計測する。ノード間の値を合算して「全体」と表示しない。計測値を取れないノードは個別に未対応または取得失敗とする。

Issue の受け入れ条件は、ホーム画面への CPU・メモリ・ネットワーク送受信量の表示、対象・単位・時点または期間の明示、調整可能な取得間隔、初回・失敗・欠損の表示、過剰負荷を防ぐ頻度制限、および算出方法の文書化である。

## 表示する値と計算

| 指標 | 対象と取得元 | 表示と算出 | 注意点 |
| --- | --- | --- | --- |
| CPU 使用率 | 選択した1台のホスト全体。Node.js 標準の `node:os` モジュールが返す全論理 CPU の時間値を2回読み、差分を使う | `100 × (全時間差分 − idle時間差分) ÷ 全時間差分`。全論理 CPU の合計を分母とし、ホスト全体で 0–100% に正規化する。取得した2時点と実経過ミリ秒も表示する | サンプル間隔内の平均であり、瞬間値ではない。初回、差分ゼロ、時刻・カウンター不整合では割合を出さず状態を表示する |
| メモリ | 選択した1台のホスト全体。`node:os` の `totalmem()` と `freemem()` | 総量 = `totalmem()`、空き量 = `freemem()`、使用量 = 総量 − 空き量、使用率 = 100 × 使用量 ÷ 総量。容量は2進単位の GiB（必要なら小さい値は MiB）で表示する | プロセス単体の使用量ではない。OS が利用可能として報告する物理メモリの残量を使い、プロセスの予約量とは呼ばない。総量が0または取得失敗なら未対応状態とする |
| ネットワーク受信・送信 | 取得できる場合はホスト上の各ネットワーク機器別。Windows では IP Helper の `GetIfTable2` / `MIB_IF_ROW2` が候補 | 累積量は受信・送信それぞれの octet カウンターを byte として表示する。速度は2サンプル間の増分 ÷ 単調時計による実経過秒で算出し、byte/s または IEC 接頭辞で表示する。計測時点と速度の対象期間を併記する | 機器カウンターは LAN とインターネットを区別しない。したがって「インターネット通信量」と表示しない。機器ごとの「全ネットワーク送受信」とし、機器間の合算値は作らない |

CPU の初回表示は「測定中」とし、2つ目の標本を得た時点から割合を表示する。割合の計算には壁時計ではなく単調時計の経過時間を使い、時計補正の影響を受けないようにする。

## ネットワーク計測の境界と依存関係

現在の Node.js 標準 `node:os` API は CPU、メモリ、ネットワーク機器のアドレス情報を扱えるが、機器ごとの受信・送信 byte カウンターは提供しない。Windows 標準の IP Helper `GetIfTable2` は機器ごとの `InOctets` / `OutOctets` を含む表を返す候補で、Microsoft の仕様上、これらは unicast・broadcast・multicast を含む機器通過量である。これらの値だけから通信先が LAN かインターネットかを判定することはできない。

| 範囲 | 依存・対応 |
| --- | --- |
| CPU・メモリ | 新依存なし。Node.js 標準 API の範囲で実装できる。Node.js の対応 OS で同じ意味の値が得られるかは実装時に個別確認し、失敗は指標単位で未対応とする |
| ネットワーク機器一覧 | `node:os` で得られる範囲に限る。これは byte カウンターの代用にしない |
| Windows の機器 byte カウンター | OS には IP Helper があるが、Node.js から構造体を安全に読み取る標準 API はない。FFI / native binding 等の新依存、または別途審査する OS 読み取り手段が必要。依存を追加する判断は本設計では行わない。許可された取得元が決まるまで表示は「未対応」とし、別の数値で埋めない |
| LAN とインターネットの分離 | 機器 byte カウンターだけでは不可。将来別の取得元を審査しても、根拠のない振り分けは行わない |

Windows の候補仕様: [GetIfEntry2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getifentry2) と [MIB_IF_ROW2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_if_row2)。標準 API の調査ではシステム権限、資格情報、OS セキュリティ設定を追加しない。CIM が拒否された環境で再試行する設計にもしない。

## 機器の重複とカウンターの再設定

- 物理、VPN、仮想、ループバックを含め、取得元が返す機器を個別に示す。種類を確実に識別できない場合は「種類不明」とする。
- 物理機器と VPN / 仮想機器には同じ通信がそれぞれ計上されることがある。全機器の合計や、推測した「インターネット合計」を作らない。カードまたは表に「機器ごとの値。複数機器の値は重複する場合がある」と明記する。
- 画面には識別に必要な短いローカル表示名と種類だけを出す。IP アドレス、MAC アドレス、機器 GUID、ユーザー名、通信先は返さず、ログにも記録しない。安定識別子が必要な場合もプロセス内でだけ使う。
- 機器が追加・削除された場合は項目を更新する。再出現、識別子変更、OS 再起動、カウンター値の減少を新しい基準点として扱い、その標本の速度は `null` とする。負の増分や推測した wrap-around は表示しない。
- 累積量は OS カウンターが現在報告する値であり、起動時刻やサービス稼働中の累積と誤認させない。基準点の時刻とリセット状態を値に含める。取得手段がリセットを通知できない場合、カウンター減少を検出した時点で基準点を作り直す。

## 取得間隔と共有計測

- 既定 10 秒、利用者が選べる値は 5、10、30、60 秒とする。許容範囲は 5–60 秒で、5 秒未満は受け付けない。
- 1サーバープロセス・1ホストに計測器を1つだけ作り、接続中のホーム画面が要求する最短間隔に合わせて標本を取る。複数利用者への配信は同じ標本を使い、接続ごとに OS 計測を起動しない。
- 有効な通知接続はプロセス全体で最大32とする。上限を超えた接続は `503` と `Retry-After` を返す。標本取得処理は重複実行させず、前の読み取りが終わってから次を予約する。
- 画面が非表示になったらその画面の通知接続を閉じ、表示に戻ったら認証を確認して再接続する。購読者がいない時は定期取得を止める。再接続時に前回標本が新鮮ならそれを最初に送り、次の標本まで待つ。
- サーバー側では間隔値を検証し、範囲外は `400` とする。ブラウザー側のタイマーだけを間隔制限の根拠にしない。
- 最終値には取得時刻を持たせ、要求間隔の2倍を超えた場合は「古い値」と明示する。取得失敗後に最後の成功値を出す場合も、成功時刻と古い状態を隠さない。取得に失敗した指標だけを失敗状態とし、他の指標は更新を続ける。

## ホーム画面 API と認証

- ホーム画面 `/user` に、選択ノードのホスト使用状況カードを設ける。セッション詳細画面には追加しない。ノードが複数なら選択ノード名とホスト全体という範囲をカードに表示し、ノード値を横断して合算しない。
- 同一オリジンの読み取り専用 `GET /user/api/host-metrics` と通知用 `GET /user/api/host-metrics/events?intervalSeconds=10` を設ける案とする。値の形式は両方で共通にする。間隔は既存ページの `EventSource` の接続引数で渡す。
- 既存のログ SSE `/api/events` は監査ログの cursor、セッション絞り込み、再同期契約を持つため、計測値のイベントを混在させない。認証済み同一オリジン通信、`EventSource` の接続・切断・再接続、および応答終了処理の既存形を参考に、計測専用の読み取り経路を作る。
- `/user` 配下の既存認証と権限確認を必須とする。ログイン期限切れ時は通知接続を終了し、画面はログイン画面へ戻す。頻繁な読み取り、通知の再接続、バックグラウンド heartbeat はログイン idle 期限を延長しない（PR #49 の方針と整合）。そのため、バックグラウンド経路には idle 更新を伴わない認証確認を使い、人による画面操作の期限更新と分ける。
- 計測専用の新 credential、公開 MCP tool、設定変更 API、リモートコマンド実行、ファイルアクセスは追加しない。権限追加、OS 設定変更、拒否された機能の迂回をしない。既存の認証・認可境界を保ち、ノード越しの値を返す場合は既存のノード認証と認可を再利用する。
- 応答は node ID、表示名、取得時刻、指標状態、単位、CPU の測定開始・終了時刻、メモリの総量・使用量・空き量、および取得可能な場合だけ機器別 byte カウンターと速度に限定する。credential、ユーザー名、IP / MAC、GUID、通信先、コマンド、監査本文は含めない。応答は `Cache-Control: no-store` とする。

想定する最小応答:

```json
{
  "nodeId": "local-node-id",
  "scope": "host",
  "observedAt": "2026-10-02T00:00:10.000Z",
  "cpu": { "status": "ok", "percent": 18.4, "windowMs": 10000 },
  "memory": { "status": "ok", "totalBytes": 17179869184, "usedBytes": 6442450944, "availableBytes": 10737418240 },
  "network": { "status": "unsupported", "interfaces": [] }
}
```

この値は形式例であり、実測値ではない。`status` は少なくとも `measuring`、`ok`、`stale`、`unsupported`、`error` を区別する。取得失敗時のエラー本文や OS 詳細は返さない。

## 画面状態

| 状況 | 表示 |
| --- | --- |
| まだ最初の標本がない | 「測定中」 |
| 指標が利用できない | 「未対応」 |
| 読み取りが失敗 | 「取得できません。再試行します」 |
| 前回値を保持中 | 前回取得時刻と「古い値」を併記 |
| 通知切断・再接続中 | 「再接続中」。前回値を最新値として見せない |
| 取得間隔変更 | 現在値と選択値を保持して新しい通知接続に切り替える |

値や機器名は HTML として挿入せず、既存の画面描画方針に合わせてテキストとして扱う。

## 合成計測値を使うテスト駆動開発計画

実機の負荷を作らず、注入可能な計測器と固定時計を使う。最初に失敗する契約テストを作り、実装後に同じ期待値を満たす。

1. CPU 合成標本: 論理 CPU 2個について合計時間差分 10,000 ms、idle 差分 6,000 ms を与え、ホスト全体 40% と 10,000 ms の期間を期待する。初回標本と差分ゼロは割合なしを期待する。
2. メモリ合成標本: 総量 16 GiB、空き 10 GiB を与え、使用量 6 GiB、使用率 37.5% を期待する。
3. 機器合成標本: 2台の機器に別々の受信・送信カウンターを与え、受信増分 1,000 byte / 5 秒なら 200 byte/s を期待する。機器別表示のみで、合計欄とインターネット表示がないことも確認する。
4. カウンター再設定: カウンター減少、機器の再出現、初回標本では速度 `null` とリセット状態を期待し、負の値が出ないことを確認する。
5. 間隔と共有: 範囲外拒否、5 秒未満を実行しないこと、複数接続で OS 読み取り器が1回だけ動くこと、利用者ごとの配信間隔、非表示接続終了、購読ゼロで停止、32接続上限を固定時計と合成接続で確認する。
6. 失敗と認証: 各指標の例外を独立表示し、古い値に取得時刻を残すこと、無認証拒否、idle 期限を延長しないこと、応答に資格情報や個人情報を含めないことを確認する。

## 親レビューで決める事項

1. 「インターネット通信量」を厳密に求めるか、上記の機器別「全ネットワーク送受信」を要件の明示修正として受け入れるか。機器カウンターは LAN と外部通信を区別しない。
2. Windows の機器別 byte カウンターを実装する場合に限り、追加依存か別の許可された OS 読み取り手段を認めるか。標準 Node.js API のみを使う実装ではこの指標は未対応となる。
3. 32接続というプロセス上限、および 5 / 10 / 30 / 60 秒の選択肢を初期値として採用するか。

この文書は設計案であり、製品コード、追加依存、権限、OS 設定、資格情報は変更しない。
