# `RemoteDesktopMCP` 読み取り専用端末CUI設計

## 状態

設計案。ここでは製品実装、設定変更、本番起動を行わない。設計レビューと利用者確認の後に実装へ進む。

## 目的と役割

課題37の目的に沿い、利用者本人のセッション一覧、実行状態、ログ概要を端末で確認する。利用者がChatGPTからセッションを作成・操作し、CUI確認者はサービス側の端末表示だけを見る。CUI確認者はChatGPTの画面やブラウザを操作しない。

表示は対話形式と1行JSON形式にする。端末操作は更新、セッション選択、終了に限る。セッション作成、ツール実行、停止、再開、ファイル取得は行わない。

## 制約

- 既存のWeb認証とprincipalごとの所有範囲を維持する。
- 起動したOS利用者を管理者または全利用者の閲覧者とみなさない。
- cookieやMCP tokenを取り出して複製しない。新しい認証許可や認証情報の保存を設けない。
- セッション本文、コマンド、プロセス output、イベント詳細、認証情報を出力しない。
- 新しい外部依存や用語一覧の項目を追加しない。
- 既存Web JSONパネルは端末CUIの代わりではない。両者は別機能として受け入れ確認する。

## 実現方式

### 採用案：サーバーと同一プロセスの端末表示

設計上の起動名を `npm run cui` とする。これは新たに追加する提案であり、現行の `package.json`にはCUI起動コマンドがない。現行の `start` と `dev` はサーバー用である。

CUI起動は、既存の起動処理、設定検査、サービス本体、HTTP/MCPサーバーを一度起動し、同じ `Node.js` プロセス内で本人用の読み取り表示を行う。ChatGPTはその既存MCP接続から操作する。CUIはこの起動で作られたサービスだけを見る。すでに動いている別プロセスへの接続や、稼働中サーバーの置き換えはしない。

サーバーは既存のローカル待受と`BASE_URL`、TLS、接続中継設定を使う。ポート競合時は理由を表示して終了する。既存プロセスの強制終了や設定上書きは行わず、別の状態APIも設けない。

### 今回採用しない案：独立CLI接続

別プロセスのCLIが現在のユーザーAPIを読む認証手段はない。APIは認証済みブラウザのcookieとprincipalを使い、MCP tokenを受け付けない。cookie抽出・複製やMCP tokenの転用をして接続しない。

独立CLIを将来設ける場合は、読み取り専用の認証許可、tokenの期限・失効、API側の認証境界、認証情報を保存しない利用方法を別設計し、明示承認を得る。今回は対象外とする。

## 起動・認証・端末の結び付け

未認証状態では、端末には待機案内だけを出し、セッション情報を取得しない。利用者は通常の `/user/login` から既存のGoogleまたはローカル開発用ログインを行う。Googleの戻り先とWebサーバーは既存のまま使い、ログイン後もサーバーを稼働させる。Google利用者識別子の登録用の運用CLIは、利用者ログインに流用しない。

起動した端末とブラウザ利用者を結び付ける。

1. CUI起動ごとに、プロセス内で暗号学的に安全な乱数から12文字以上の一回限りの端末連携番号を生成する。有効期間は5分、入力上限は5回とする。番号とその検証値をファイルや監査ログに保存しない。
2. CUIは既定ブラウザで既存ログイン画面を開く。開けない場合はURLを表示する。ChatGPTのブラウザは操作しない。
3. 利用者は自分のアカウントでログインし、認証済み `/user` 画面で「自分のセッション情報をこの端末に表示する」を選び、端末連携番号を入力する。
4. 送信は既存の接続元確認、偽造要求対策、ログイン済みprincipalを通す。新しいAPI経路は作らず、既存 `/user` の画面送信として処理する。連携番号は端末起動とログインの相関にだけ使い、認証情報として使わない。
5. サーバーは有効期限、入力回数、一回性、送信元のログイン状態を検証する。成功時はprincipalとログイン有効状態を同一プロセス内のCUIに渡す。cookie値、token、メールアドレス、Google利用者識別子は渡さず、表示もしない。
6. 最初の有効な申請を保留し、別ブラウザや別principalからの申請で置き換えない。CUIは申請を保留中とだけ表示し、データを取得しない。利用者はブラウザ画面のログイン先を確かめた上で、端末でも保留中の申請を承認する。間違った申請は拒否して番号を失効させ、再連携には新しい起動を要求する。
7. 利用者のブラウザ確認に加え、端末側でも保留中の連携を承認してから取得を始める。どちらかの確認がない場合、出力は待機状態のままとする。表示先は承認したログイン状態に固定し、後から他のブラウザやprincipalが奪えないようにする。

連携番号は十分な乱数で生成し、URL、コマンド履歴、設定ファイルに含めない。起動URLにも番号を含めない。番号入力とブラウザでの確認、端末での確認をすべて必要とする。同じOS利用者・LANにいることだけでは認可しない。期限切れや回数超過の番号は使えず、再連携はCUIを終了して新たに起動する。

## principalと所有範囲

表示先はブラウザで明示承認された一つのログイン状態に固定する。同一principalの別ブラウザや別principalの後続ログインも、現在の表示先を変更できない。OS管理者権限による閲覧も行わない。

session一覧・operation・logsの取得は既存のprincipal別ユーザー処理を再利用する。本人所有のsessionだけを表示し、owner確認はサーバー側で行う。本人の所有範囲外は既存どおり404として扱う。管理画面用の全利用者ログ読み取り関数を未filterで使わず、接続IDからownerを推測しない。

ChatGPT接続とユーザー画面のログインは同じprincipalである必要がある。異なるprincipalで作られたsessionは表示しない。ローカル開発用パスワード認証方式でも、既存の登録利用者で認証し、その利用者の所有範囲だけを表示する。

## 表示項目と形式

既存の `authenticated-console-json-view-design.md` の固定schemaを再利用し、API応答の余分なfieldを展開しない。

Session:

- `sessionId`: string
- `purpose`: stringまたはnull
- `workingDirectory`: stringまたはnull
- `createdAt`: offset付きISO日時
- `lastAccessAt`: offset付きISO日時
- `state`: `active`、`closed`、`expired`、`unavailable`

Operation:

- `operationId`: string
- `connectionId`: string
- `status`: `running`または`terminating`
- `startedAt`、`endedAt`: APIに値がないためnull

Log:

- `logId`: string
- `timestamp`: offset付きISO日時
- `type`: string

各配列は最大200件とする。ログは既存APIのlimitと最新pageを使い、全履歴取得やファイル取得機能を追加しない。上限に達した場合は一部表示と明記する。APIにない値を推測せず、必須field、型、列挙値が不正なら取得結果を破棄して内容を消す。

対話表示は起動した端末だけに出す。1行JSON形式では1行に1状態をstdoutへ書き、起動案内、連携番号、確認待ち、エラーはstderrへ書く。ファイルへの自動保存はしない。対話用端末がない場合は連携・出力を開始せず終了する。利用者が明示的にリダイレクトしたstdoutの管理は利用者の責任とする。

両形式は同じ許可項目一覧を使い、HTMLとして解釈しない。cookie、token、Google認証属性、メールアドレス、コマンド、プロセス output、任意イベント詳細、エラー本文、他利用者情報を出力しない。作業ディレクトリとpurposeも本人用の限定fieldとして扱い、共有ログへ記録しない。

## 更新・失効・終了

初期状態は未認証。ブラウザと端末の両確認が完了するまで一覧・状態記録を取得しない。承認後は同じサービスの読み取り処理から上限付きの最新状態を定期取得する。並行要求、無制限な取得、無制限な履歴保持を避ける。

次の場合は連携番号、ログイン有効状態、表示modelを破棄して端末表示を消す。

- 承認したログイン状態のログアウトまたは期限切れ
- CUIまたはサーバーの終了、中断操作
- 利用者が端末表示を解除
- owner不一致、認証失効、想定外応答、認証境界エラー

別利用者のログアウトでは現在の表示を止めない。同一principalでも承認したログイン状態が失効したら自動再連携しない。再表示には新しいログインと両側の確認を求める。終了後に返った遅延応答から表示を復元しない。

## 既存JSONパネルから再利用するもの

固定schema、API fieldの型検証、200件上限、session選択時のowner範囲、異常時の内容消去、一部表示の明示、競合要求と遅延応答の破棄は再利用候補とする。応答変換は純粋関数として分離し、ブラウザと端末が同じmodelを使う。

画面要素の生成、ボタン、fetch、AbortController、ブラウザ内のstatus表示は端末表示に流用しない。現行JSONパネルのテストがgreenでも、端末表示、連携番号、ログイン失効、ChatGPT作成sessionの端末確認が済むまではCUI完了としない。

## 設定と秘密値

既存の `.env`、`configFromEnv()`、`bootstrap.ts` の検査を再利用する。`BASE_URL`、`PORT`、`FILE_ROOTS_JSON`、`DATA_DIR`、既存認証方式とその秘密値要件を維持する。Google方式では既存認証秘密値と戻り先設定が必要だが、CUIは値を作成・変更・表示しない。利用者または運用者が本人の管理する既存手順で設定する。

設定不在、保護ファイル検査失敗、不正なURL・戻り先、`PORT`競合では起動拒否とする。自動設定作成、秘密値の生成・複製、OSのアクセス権・保護設定・認証設定の変更、稼働中サーバーの置き換えをしない。

## 安全な試行手順

1. 利用者または運用者が、本番とは別のendpoint、認証設定、`DATA_DIR`、テスト用ファイルrootを既存手順で用意する。機能が本番秘密値のコピーを要求しない。
2. 利用者が非本番環境でCUIを別プロセスとして起動する。`PORT`競合なら終了し、稼働中プロセスを終了・置換しない。
3. 起動案内、連携番号、待機状態だけを確認する。利用者が自分のブラウザで認証し、端末表示を明示的に承認する。
4. 利用者がChatGPTから同じ非本番MCP endpointへ接続し、同一principalのsessionを作成・操作する。CUI確認者はChatGPT画面を操作せず、端末だけを見る。
5. 本人所有sessionだけが現れ、状態記録概要が更新され、ログアウト、期限切れ、中断操作で内容が消えることを確認する。
6. 本番または稼働中サービスへの切替は別の運用判断とする。初回確認を本番設定で行わない。

起動に秘密値が必要でも、利用者・運用者本人が既存の手順で設定する。作業者が値を尋ねる、読み取る、別ファイルへ複製することはしない。非本番環境や承認済み設定を用意できなければ、起動・検証済みと報告しない。

## テスト駆動開発と受入れ確認

実装時は端末機能の失敗テストを先に作り、模擬サービスと固定時計で確認する。実秘密値、本番サーバー、ChatGPTブラウザ操作を自動テストに含めない。

- 連携番号の期限、試行上限、一回性、誤入力、再発行、起動ごとの分離を確認する。
- 未認証、偽造要求対策の不備、別principal、同principalの別ログイン状態、owner外sessionを拒否し、端末出力が空であることを確認する。
- ブラウザ側の明示確認と端末側の承認の両方がなければ結び付かず、最初の承認後に別利用者から奪えないことを確認する。
- ログアウト、期限切れ、解除、中断操作、サーバー終了で連携と表示内容が消え、遅延応答で復活しないことを確認する。
- schema必須field、nullable、列挙値、型不正、200件上限、一部表示、未知fieldの非出力を確認する。
- 制御文字を安全に扱い、認証情報、Google認証属性、メールアドレス、command、output、イベント詳細、エラー本文が対話表示・1行JSONに出ないことを確認する。
- stdoutの各行がJSONとして読め、案内と確認入力はstderr、対話用端末がない場合は情報を出さず終了することを確認する。
- 読み取りがsession、operation、audit状態を変更しないことを確認する。
- 最終統合確認では、利用者自身が非本番ブラウザ認証とChatGPTでのsession作成を行い、CUI確認者はサーバー端末出力だけを確認する。既存API テストのgreenだけを完了根拠にしない。

## 依存関係と変更範囲

現行の `package.json`に端末表示用の依存はない。実装では実行環境の標準入出力と対話端末機能と既存依存だけを使う。依存一覧、依存固定ファイル、lint 用語一覧を増やさない。`npm run cui` は設計上の起動名で、現時点では存在しない。

この文書は設計であり、機能実装済み・起動可能・ChatGPT連携確認済みを意味しない。実装、非本番設定、利用者によるブラウザとChatGPTの確認、本番運用判断は後続作業とする。
