# 使用者コンソールと緊急停止

## 目的と適用範囲

Issue #12 の設計。使用者提供の `RemoteDesktopMCP_user_console_emergency_stop_spec.md` を要件資料とする。
管理者はサーバーの運用を担当し、使用者は自身の接続、呼び出し履歴、実行状態を確認する。
同じ人物が両方を担当していても、ログイン状態と認可を区別する。
本変更は単一サーバープロセスの構成を対象とする。複数サーバー構成では、状態ストアと停止通知の共有が必要になる。

## 認証と認可

使用者コンソールはブラウザー用の認証セッションを持つ。
Google の検証済み発行者と subject を、既存 MCP 認証と同じ主体識別子へ変換する。
ローカル開発のパスワード認証では、検証済みアカウントを使用する。
リクエスト引数の主体識別子を信頼しない。
使用者の許可設定は各リクエストで確認し、管理者設定だけでは使用者権限を付与しない。
管理者セッション、使用者セッション、MCP アクセストークンは用途を分離する。
特に MCP から停止解除を呼び出すツールは設けない。

ブラウザーによる状態変更は POST に限定し、同一オリジン検証とセッションに結び付いた CSRF 対策を行う。
Cookie は HttpOnly、SameSite、公開 HTTPS では Secure を指定する。
認証・状態・履歴の応答にはキャッシュ抑止を設定し、表示値は HTML エスケープする。

## 接続と操作の識別

既存の MCP HTTP トランスポートはリクエストごとに生成されるため、TCP 接続を操作の所有単位にしない。
RDMCP の論理セッションを接続の単位とし、発行した識別子を Connection ID として追跡する。
セッション作成前の呼び出しにも受信を識別できる値を割り当てる。
各ツール呼び出しに Operation ID を割り当て、検証済み主体、接続、停止世代を関連付ける。
ChatGPT の Chat ID は必要としない。

呼び出し履歴は受信時刻、開始・終了時刻、所要時間、ツール名、対象概要、状態を持つ。
状態は `running`、`succeeded`、`failed`、`cancelled`、`rejected` とする。
引数全体や秘密値を無条件に記録せず、対象概要は長さを制限して機密値を除去する。
履歴の閲覧は必ず認証済み主体で絞り込み、クライアントから指定された他人の接続を参照させない。

## 停止状態と永続化

主体ごとに `stopped`、`stop_generation`、`stopped_at`、`stop_id` を保持する。
状態は DATA_DIR 内の保護されたファイルに保存し、一時ファイルと置換により部分書き込みを防ぐ。
保存完了と応答する前にファイルを同期し、置換後の耐久性について OS が提供する範囲を確認する。
起動時に状態を読み込んでから実行を受け付ける。状態が破損している場合は起動を失敗させる。
停止・再開の更新を直列化し、同時操作で世代や停止状態が巻き戻らないようにする。
停止をメモリへ反映して実行受付を遮断してから、永続化と後処理を行う。
永続化に失敗した停止は成功と表示せず、そのプロセスでは遮断を維持する。
再開の永続化に失敗した場合も実行を許可しない。
メモリだけの遮断では保存失敗後の再起動を保護できないため、未完了の更新を検出できる記録を設ける。
保存装置へ一切記録できない障害時は、停止が再起動後にも保存されると保証してはならない。

## 停止フロー

1. 使用者のブラウザー認証と状態変更の正当性を確認する。
2. 停止世代を進め、停止状態へ遷移し、新規実行の受付を遮断する。
3. 停止状態を永続化する。
4. 対象主体の既存接続を無効化し、進行中の操作をキャンセルする。
5. 対象主体のプロセスと転送等の資源を停止・解放する。
6. 結果を記録し、使用者コンソールに停止状態と未確認の後処理を表示する。

停止受付を長時間実行中のプロセス用ロックの後ろに並べない。
実行直前と非同期待機からの復帰後に停止・世代を確認する。
停止時にまだ PID が返っていない起動要求も、PID 判明後に回収して停止対象とする。
停止前に待機していた要求は、再開後も古い世代で実行させない。
他主体の接続やプロセスを停止するために、共有バックエンドを無差別に終了してはならない。

## 停止拒否と再開

停止中は新規セッションを経由してもツール実行を拒否する。
応答には `USER_STOP_REQUESTED`、本人が停止を指示した旨、再試行や別経路への迂回を行わない旨、停止 ID と世代を含める。
サーバー側の拒否を強制し、クライアントが応答文を尊重することには依存しない。

使用者コンソールの明示的な再開操作によってのみ停止を解除する。
再開しても停止前の接続を復活させず、新しい論理セッションの作成を要求する。

## 停止の保証と制約

受付拒否、接続失効、処理の中断要求、OS プロセス終了の確認は異なる状態として扱う。
停止済みという表示だけで、OS の全子孫プロセスが終了したと断定しない。
バックエンドがキャンセルに対応しない処理は、実行を終えてから結果だけを破棄しても中断したことにはならない。
既に完了したファイル変更や外部サービスへの作用は停止によって取り消せない。
任意コマンドにはサーバーと同じ OS ユーザー権限があるため、本機能は OS 権限による隔離ではない。
具体的に中断可能な処理、終了確認方法、残る制約は実装と検証結果に合わせて本書へ追記する。

### Windows のプロセス所有管理

固定版 Desktop Commander の終了要求は根プロセスに対するもので、子孫全体の終了を保証しない。
この経路だけの実装では、元資料の「関連プロセスを停止する」を完全には満たさない。
そのため、Windows ではコマンド起動を専用の補助プロセスで包み、Job Object に起動したプロセスと子孫を所属させる。
対象プロセスを一時停止状態で生成し、所有管理への登録に成功してから実行を開始する。
補助プロセスは所属するプロセスがなくなるまで存続し、終了時に残る所属プロセスを終了させる。
これにより、コマンド本体が先に終了して子孫だけが残る場合も所有関係を保持する。
補助プログラムの作成や所有管理への登録に失敗したときは、管理外の起動へ切り替えず拒否する。

バックエンドの起動時点で検証済み主体と操作 ID を関連付ける。
通常の起動応答が返る前やタイムアウトした後も、非公開の停止経路から本人の管理下プロセスを停止できるようにする。
外部公開の MCP ツールには、この非公開経路や所有者指定の引数を公開しない。
利用する固定版バックエンドの版と必要な内部 API を検証し、非互換な版では起動を拒否する。

既存の独立したサービスに依頼した処理や、同じ OS 権限による意図的な管理外への移動を隔離する仕組みではない。
Windows 以外ではバックエンドが保持する根プロセスへ終了要求を送り、子孫全体の終了は保証しない。
停止処理はバックエンド内の所有記録と照合し、応答が得られない場合に未検証の PID を終了してはならない。
終了を確認できない場合は監査へ記録し、停止状態を維持する。停止中は画面から停止処理を再試行できる。
管理下の子孫、親の先行終了、起動応答待ち、別主体との同時実行を実機テストで確認する。

### 副作用の制約

停止前にバックエンドへ送信済みのファイル編集は、停止後に完了する場合がある。
`file_patch` の送信済み `edit_block` は中断せず、その結果を `USER_STOP_REQUESTED` に置き換える。
この結果抑止は編集自体の中断ではなく、既に行われた変更も取り消さない。
新規受付の遮断とプロセス停止とは別の制約として、実装報告と PR に明記する。

## 検証項目

- 本人だけのログ表示、管理者との認可分離、別主体や偽造主体の拒否。
- Origin と CSRF 検証、MCP トークンからの停止解除不可。
- 停止中の新規接続・新規実行拒否と、再開後の旧接続拒否。
- サーバー再起動後の停止維持、状態破損、永続化失敗。
- 実行待ち・起動待ち・停止と再開の競合と、遅れて返る PID の停止。
- プロセス停止結果、転送中断、通常の操作・認証の回帰。
- 型検査、Lint、ビルド、全体テスト、Windows と Ubuntu の CI。

実装は GPT-5.6 Terra high と GPT-6 Luna high、レビューは GPT-6 Sol high で担当する。
レビュー指摘と必要な検証を完了してからマージする。
