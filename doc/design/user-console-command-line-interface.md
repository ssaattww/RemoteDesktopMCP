# 使用者コンソールのコマンドライン表示

## 目的

使用者コンソールで確認できるセッション一覧、実行状態、操作履歴、コマンド出力を、端末から確認できる CUI を追加する。
Web 画面を置き換えるものではなく、同じ使用者向け情報を別の表示方法で参照できるようにする。

初期版は読み取り専用とする。
停止、再開、セッション終了、設定変更など、サーバー状態を変更する操作は提供しない。

既存の認証・認可、監査ログ、ページング、更新通知を再利用し、CUI が `DATA_DIR` を直接読んだり、
Web と同じ集計処理を別に実装したりしない。

関連する既存設計は次のとおり。

- [使用者コンソールと緊急停止](user-console-emergency-stop.md)
- [ファイル操作の基準パスと使用者ログの更新](file-paths-and-live-logs.md)
- [機能要件](functional-requirements.md)

## 適用範囲

初期版で扱う情報は次のとおり。

- 本人のセッション一覧
- セッションの有効状態、作成日時、最終アクセス日時、用途、作業ディレクトリ
- 本人の実行中操作
- 操作履歴
- `process_start` の実行目的、コマンド、出力、終了結果
- 使用者の停止状態
- ログの新着通知

初期版では次を扱わない。

- 緊急停止と再開
- セッションの作成、終了、延長
- プロセスの停止
- ファイル操作
- 管理者向け情報
- 他の使用者のセッションやログ
- 認証情報の永続保存

## 基本方針

CUI は既存の使用者コンソール API を呼び出す薄いクライアントとする。

現在の Web 画面が使用している次の読み取り経路を正とする。

- `/api/console-state`
- `/api/logs`
- `/api/events`

CUI は監査ログファイルやメモリ上のサービス状態へ直接アクセスしない。
既存 API に必要な情報が不足する場合は、Web と CUI が共有できる読み取り API または共通の読み取りモデルを拡張する。
CUI 専用に監査ログの解析、セッション集計、実行中操作の判定を複製しない。

Web と CUI で表示形式は分ける。
認証済み主体の決定、本人データへの絞り込み、秘密値除去、カーソル検証、新着判定は共有する。

## 認証と認可

### 原則

CUI のために固定トークン、共有パスワード、管理者権限による迂回経路を追加しない。
ローカル端末から実行されたことだけを本人確認の根拠にしない。

CUI が利用する主体は、既存の使用者コンソールと同じ認証済み主体でなければならない。
本人以外のセッション ID を指定した場合は、既存 API と同じく存在を開示せず 404 とする。

CUI 用の資格情報を設定ファイル、`DATA_DIR`、ホームディレクトリ、資格情報保管庫へ保存しない。
コマンドライン引数にもトークンや Cookie を渡さない。

### ブラウザーからの一時的な引き渡し

初期版では、既存 Web 認証を利用した一時的な引き渡しを行う。

1. CUI は十分な長さの `state` と検証用秘密値を生成し、`127.0.0.1` の空きポートだけで一時待ち受けする。
2. CUI は公開 `BASE_URL` 上の使用者コンソールに認証要求 URL を表示し、可能なら既定ブラウザーで開く。
3. サーバー側は既存の使用者ログイン処理で本人を確認する。未ログインなら通常の Web ログインへ進める。
4. 認証後は確認画面を表示し、既存の CSRF 検証を通った明示操作でのみ一回限りの認証コードを発行する。
5. 認証コードは主体、`state`、検証用秘密値の照合値、有効期限へ結び付ける。短時間で失効し、一度交換したら再利用できない。
6. CUI はローカル待ち受けで認証コードを受け取り、検証用秘密値とともに HTTPS で交換する。
7. 交換後に得た使用者セッション資格情報はプロセスのメモリだけに保持し、終了時に破棄する。

この資格情報は読み取り API だけで受け付ける。
緊急停止、再開、管理者 API、MCP ツールの認証には使用できない。
有効期限は既存の使用者ログイン期限を超えない。
認証が失効したら自動的な権限拡張や別経路への切り替えを行わず、再認証を要求する。

ブラウザー用 Cookie と CUI 用の一時資格情報は、同じ使用者セッション判定へ到達するよう共通化する。
主体の許可確認を CUI 側に複製しない。

## コマンド構成

実装時の入口は npm script とビルド済み JavaScript の両方から同じ処理を呼び出せる形とする。
実行ファイル名の固定は配布方法が決まるまで設計上の要件にしない。

初期版の論理コマンドは次のとおり。

| コマンド | 目的 |
| --- | --- |
| `sessions` | 本人のセッション一覧を表示する |
| `status` | 停止状態、有効セッション数、実行中操作を表示する |
| `logs` | 操作履歴とコマンド出力を表示する |
| `logs --watch` | 新着ログを継続して表示する |

共通オプションは次のとおり。

- `--base-url <URL>`: 接続先を指定する。秘密情報ではない。未指定時の既定値は実装時に明示する。
- `--session <ID>`: 対象セッションを本人の範囲で絞る。
- `--json`: 機械処理向け出力へ切り替える。

`sessions` は `--active` を受け付け、有効なセッションだけを表示できるようにする。

`logs` は `--limit <1..200>` を受け付け、既存 API と同じ上限を使う。
カーソルを利用した過去ログ取得は初期版でも内部処理に使用するが、カーソル文字列を通常の人向け操作として要求しない。

## 人向け表示

`sessions` は一行一セッションの表形式とし、少なくとも次を表示する。

- 状態
- 用途
- Connection ID
- 作成日時
- 最終アクセス日時
- 作業ディレクトリ

`status` は停止状態、有効セッション数、実行中操作数を先頭に表示する。
実行中操作がある場合は Operation ID、Connection ID、ツール名またはプロセス、状態を表示する。

`logs` は人が追いやすいよう時系列で古い項目から新しい項目へ表示する。
`process_start`、複数回の出力、終了結果は同じプロセス単位で関連が分かる表示にする。
実行目的とコマンドは通常表示し、出力は端末向けに区切りを付ける。

秘密値を表示しない要件は Web と同じであり、CUI 側で生の引数や保存前の値を追加表示しない。

## JSON 出力

`--json` は端末装飾、色、進捗表示を混ぜない。

`sessions --json` はセッション配列と更新時刻を JSON オブジェクトとして出力する。
各セッションの項目名は `/api/console-state` の項目名を使用する。

`status --json` は `/api/console-state` の読み取り結果をそのまま表現する。
CUI 独自の状態判定を追加しない。

`logs --json` は `/api/logs` のページ情報を保持し、項目、最新カーソル、最古カーソル、前後ページの有無を失わない。

`logs --watch --json` は長時間のストリームになるため、JSON 配列ではなく一行一レコードの JSON とする。
通常の新着ログは `type` を `log` とし、既存ログ項目を `item` に保持する。
再同期が必要な場合は `type` を `resync-required` とする。
認証失効などログ以外の制御状態も個別レコードとして出力し、通常ログと区別する。

時刻は JSON では既存 API の ISO 8601 表現を維持する。
人向け表示だけで端末向けの日時表現へ整形する。

## 監視モード

`logs --watch` は `/api/events` の更新通知と `/api/logs` のカーソル取得を組み合わせる。
サーバー側の通知を受け取るたびに全ログを読み直さない。

開始時は上限付きで現在のログを取得し、最新カーソルを保持する。
`logs-available` を受け取ったら `after` を使って新着だけを取得し、追い付くまで上限付きページを繰り返す。

次の場合は再同期扱いとする。

- サーバーから `resync-required` を受け取った
- ログカーソルが失効した
- 新着件数が保持範囲を超えた
- ストリーム再接続後に継続位置を検証できない

再同期時は最新の上限付きページを取得し直し、人向け表示では再同期したことを明示する。
JSON では制御レコードを出してから取得し直したログを出力する。
取得できなかった過去ログが存在する可能性を隠さない。

ハートビートは接続維持に使用するが、通常出力には表示しない。
一時的な通信失敗は上限付きの待ち時間で再接続する。
認証失効は再接続で回避せず終了し、再認証を要求する。

メモリ内に保持するログ件数は上限を設ける。
監視時間に比例してメモリが増え続ける実装にしない。

## エラーと終了

引数不正、認証失敗、対象不存在、通信失敗を区別して標準エラーへ簡潔に出力する。
JSON 出力時も通常結果の標準出力へ人向けエラー文を混ぜない。

初期版では少なくとも次を区別する。

- 正常終了
- 引数不正
- 認証失敗または認証失効
- 対象セッションが存在しない、または本人に見えない
- サーバーまたは通信の失敗
- 利用者による割り込み

具体的な終了コードは実装時にテストとともに固定し、後から同じ意味を変更しない。

## セキュリティ要件

- CUI は HTTP API の認可結果を信頼し、ローカルで閲覧範囲を広げない。
- 本人以外のセッションを列挙できる管理者用の隠しオプションを設けない。
- 認証コードと一時資格情報は標準出力、ログ、監査ログ、コマンドラインへ出さない。
- 一時待ち受けは `127.0.0.1` に限定し、LAN や全インターフェースで待ち受けない。
- 認証コードは一回限りとし、短い有効期限、`state`、検証用秘密値の照合を必須とする。
- CUI 用資格情報をファイルへ保存しない。
- 読み取り専用資格情報で状態変更 API を呼べないことをサーバー側で強制する。
- 既存の秘密値除去、長さ制限、監査ログの主体分離を維持する。
- CUI の追加を理由に CSRF、Origin、HTTPS、Cookie 属性など Web 側の保護を緩和しない。

## 実装時の共通化境界

`mountUserConsole` に存在する使用者判定や状態集計を CUI へコピーしない。

実装時は次の境界を優先する。

1. Web Cookie と CUI の一時資格情報から、同じ認証済み主体へ解決する認証境界。
2. 認証済み主体と任意のセッション ID から、本人に見える状態だけを返す読み取り境界。
3. 監査ログのページング、カーソル、新着件数、更新購読を提供する既存サービス境界。
4. Web HTML、ブラウザー JavaScript、端末表示、JSON 表示という表示境界。

既存 API の応答生成が Web ルート内へ埋め込まれていて再利用しにくい場合は、先に型付きの読み取り関数へ抽出する。
Web ルートと CUI 向け API が同じ関数を呼ぶ構成にしてから CUI 表示を追加する。

## 検証方針

### 認証・認可の検証

- 未認証の CUI が使用者 API を読めない。
- 一回限りの認証コードを再利用できない。
- `state` または検証用秘密値が一致しない交換を拒否する。
- 認証コードと一時資格情報が期限切れ後に利用できない。
- CUI 資格情報を使用して緊急停止、再開、管理者 API を実行できない。
- 他主体のセッション ID を指定しても情報を取得できず、404 になる。
- 使用者の許可を外した後は、既存 Web と同じ基準で CUI も拒否される。

### 表示と JSON

- `sessions`、`status`、`logs` が既存 Web/API と同じ元データを参照する。
- 人向け表示の整形でセッションや状態を欠落させない。
- `--json` の標準出力が機械処理可能な JSON だけになる。
- 監視時の一行一レコード JSON を逐次解析できる。
- トークン、Cookie、秘密値、認証コードが出力に含まれない。

### 監視

- 新着通知後に `after` カーソルで新着だけを取得する。
- 複数ページの新着を順序どおり取得する。
- カーソル失効、通知あふれ、再接続で再同期へ移行する。
- ハートビートだけではログを再取得しない。
- 長時間監視でも保持件数が上限を超えて増え続けない。
- Ctrl+C で待ち受け、HTTP 接続、タイマーを解放する。

### 既存機能への影響

- Web 使用者コンソールのログイン、一覧、詳細、更新通知が従来どおり動作する。
- 緊急停止と再開の認証・CSRF 要件を変更しない。
- MCP の認証・認可とツール実行経路を変更しない。
- 管理者画面の権限を変更しない。
- Windows と Linux で端末出力と監視終了が成立する。

## 実装前の完了条件

実装へ進む前に、次を満たすことを設計レビューで確認する。

- 初期版が読み取り専用である。
- CUI が既存 API と認証・認可を再利用する。
- 認証情報の永続保存を追加しない。
- JSON 出力と監視モードの契約が明確である。
- 他主体の情報を見られないことをサーバー側で保証する。
- Web と CUI に同じ集計処理を重複実装しない。
- セキュリティ保護を緩和する変更を含まない。
