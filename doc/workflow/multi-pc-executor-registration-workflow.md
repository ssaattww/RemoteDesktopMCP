# 複数 PC 実行ノード追加・登録 作業手順

## 目的

複数 PC を実行ノードとして追加・登録する機能を、設計、実装、検証、通常確認、独立最終確認の順に分離して進める。

この文書は製品仕様ではなく作業手順を定義する。
製品仕様は `functional-requirements.md` と `multi-pc-architecture.md` を正とする。

## 作業範囲

この作業手順の対象は次のとおり。

- 統括ノードと複数の実行ノードのローカル設定。
- 実行ノードから統括ノードへの tailnet 内接続。
- 事前共有鍵、nonce、HMAC-SHA-256、HKDF-SHA-256 によるノード相互認証。
- 登録済みノード一覧、接続状態、利用可能な操作、ファイルルート情報の管理。
- ファイル操作、転送、プロセス操作の `node_id` による振り分け。
- 再接続、切断、重複接続、実行ノード再起動時の状態遷移。
- 使用者の実行停止状態を複数ノードへ伝える処理。
- PC 追加、事前共有鍵更新、登録解除の利用者向け手順。
- 統括ノード1台と実行ノード2台以上を使う実機確認。

次は対象外とする。

- 統括ノードの自動切り替え。
- 複数統括ノードの同時運用。
- ChatGPT または公開 HTTP API からのノード登録、削除、事前共有鍵変更。
- 切断時に別ノードへ自動的に振り替える処理。
- 1つの操作を複数ノードへ同時配信する機能。

## セッション分離

複数 PC 実行ノード追加・登録の作業では、他作業の RemoteDesktopMCP セッションを再利用しない。

各工程は工程専用の RemoteDesktopMCP セッションを開き、対象の Git 作業ツリーの絶対パスを固定する。
工程終了時はそのセッションを閉じる。
通常確認と独立最終確認は、設計・実装工程のセッションを再利用せず、別セッションで開始する。

同じ機能の作業内でも並行作業が必要な場合は、同じ Git 作業ツリーを共有しない。
別の作業ツリーと別の Git 分岐を使用し、合流点を明示する。

## 共通の完了条件

作業開始時に `.github/workflows/lint.yml` の診断資料保存設定を確認する。
既存の自動検証定義がテスト結果、標準出力、標準エラー、実行結果、環境情報を成功・失敗の両方で保存する限り、診断目的だけの重複定義は追加しない。

実装変更はテスト駆動開発で進める。

1. 対象契約を固定する試験を追加する。
2. 追加した試験が期待した理由で失敗することを確認する。
3. 最小実装で成功へ変える。
4. 関連する回帰試験を実行する。
5. 確認可能な小さな論理単位で `git commit` と `git push` を行う。

自動検証の確認では、対象プルリクエストの現在の `HEAD SHA` と実行記録の `head_sha` が完全一致する記録だけを使用する。
HEAD 更新後は新しい HEAD に対応する実行記録を確認し、一致する記録がなければ自動検証未実施として扱う。

## 設計契約の固定

### 入力

- 複数 PC 実行ノード追加・登録の要件。
- `doc/design/functional-requirements.md`。
- `doc/design/multi-pc-architecture.md`。
- 現行の単一ノード実装と公開接続設計。

### 作業

- 単一ノード前提が残る API、状態、設定を列挙する。
- ノード間通信、認証、接続状態、再接続、重複接続を固定する。
- 役割ごとの起動条件、ローカル設定形式、実行ノードの `node_id` 生成から事前共有鍵設定までの初期設定順序を固定する。
- `node_list` をセッション開始前に利用できる発見契約とし、複数ノード時の `session_open` の対象選択を固定する。
- セッションを対象ノード1台とそのノード上の作業ディレクトリへ固定する。
- 公開 `transfer_id` と論理プロセスID、実行ノード内 `remote_transfer_id` と `remote_process_id` の所有境界、世代失効、再起動時の扱いを固定する。
- 使用者の実行停止状態を遠隔実行ノードへ伝える契約を固定する。
- PC 追加、事前共有鍵更新、登録解除の手順を固定する。

### 完了条件

- 実装者が追加判断をせず試験項目へ落とせる。
- 機能要件と詳細設計に矛盾がない。
- 文書形式検査と設計用語検査が成功する。

## ノード設定と暗号方式

### ノード設定・暗号方式の失敗確認

実装前に、少なくとも次の試験が期待理由で失敗することを確認する。

- 役割別必須設定。
- 実行ノード専用構成では接続先、ポート、事前共有鍵が3項目とも未設定または3項目とも設定済みの状態だけを許可し、部分設定を拒否する。
- `set-coordinator` を実行ノード専用構成だけに許可し、3項目を1回の原子的設定更新で保存する。
- 永続 `node_id`。
- 事前共有鍵の32バイト base64url 検証。
- `executor_generation`、`desktop_commander_generation`、`remote_transfer_id`、`remote_process_id` の16バイト乱数・末尾の `=` を付けない base64url 22文字検証。
- 未登録 `node_id`、誤った事前共有鍵、不正 nonce、不正 HMAC、未対応プロトコル版の拒否。
- セッション鍵と `connection_id` の既知入力試験。
- `sequence` の再送、逆行、改ざんの拒否。

### ノード設定・暗号方式の成功確認

ローカル専用のノード設定保存、管理用コマンド、暗号処理を実装する。
秘密値を監査ログ、エラー、Desktop Commander 子プロセス環境へ渡さない。

## ノード接続と登録状態管理

### ノード接続・登録状態の失敗確認

- `coordinator`、`executor`、`both` の各役割での起動と、実行ノード専用構成の接続先未設定状態。
- Tailscale IP 以外へのノード間待ち受け拒否。
- 実行ノードから統括ノードへの接続。
- 認証済み生存確認による接続状態更新。
- `active` 接続と `synchronizing` 候補の切断、再接続、置換、候補同期失敗。
- 登録解除または事前共有鍵更新時に `active` 接続と `synchronizing` 候補の両方を無効化すること。
- 実行ノード再起動時の実行ノード世代変更。
- 登録済みだが未接続のノードも `node_list` に残ること。

### ノード接続・登録状態の成功確認

ノード登録状態、統括ノード側接続受付、実行ノード側接続処理を責務ごとに分離して実装する。
新しい接続は相互認証だけでは旧 `active` 接続を置き換えず、`ready` と最新の使用者状態同期まで完了した `synchronizing` 候補だけを `active` へ昇格する。

## 公開 MCP の振り分けとセッション

### 振り分け・セッションの失敗確認

- 登録ノード1台時だけ `node_id` を省略できる。
- 登録ノード2台以上では接続数にかかわらず `node_id` が必須。
- 切断ノード、未登録ノードを拒否し、別ノードへ振り替えない。
- `node_list` がノードごとのファイルルート、利用可能な操作、接続状態を返す。
- `session_open` がセッションを対象ノード1台と作業ディレクトリへ固定する。
- `session_validate_working_directory` がプロトコル版1の必須内部操作として利用でき、外部 MCP ツール一覧と `node_list.operations` には現れない。
- セッションと異なる `node_id` を指定した操作を拒否する。
- 対象ノードの作業ディレクトリを確認できない場合に `process_start` を実行しない。

### 振り分け・セッションの成功確認

公開 MCP からローカル実行と遠隔実行を同じ振り分け契約へ集約する。
実行ノードへ任意の Desktop Commander ツール名を渡さず、RemoteDesktopMCP が定義した内部操作だけを送る。

## ファイル転送とプロセス

### ファイル転送・プロセスの失敗確認

- 転送作成時の `node_id` 固定。
- チャンク送受信、確定、状態確認、中断で実行先を変更できない。
- ノード切断中に別ノードへ転送を継続しない。
- 公開 `transfer_id` と実行ノード内 `remote_transfer_id` を分離し、実行ノード世代へ固定する。
- 公開論理プロセスIDと実行ノード内 `remote_process_id` を分離し、統括ノードが遠隔 PID を保持・送信しない。
- プロセスIDを対象ノード、実行ノード世代、Desktop Commander 世代へ固定する。
- 実行ノード再起動後に古いプロセスIDで別プロセスを操作せず、旧 OS プロセスを PID だけから復元しない。
- 統括ノードとの接続だけが切れて戻った場合は、継続している実行ノード内資源を別ノードや別世代へ結び直さない。

### ファイル転送・プロセスの成功確認

統括ノード側では公開IDと実行ノード内IDの対応だけを保持する。
実際のファイル制限、転送一時ファイル、PID 所有確認は対象実行ノード側でも再検証する。

## 使用者の実行停止

### 使用者停止の失敗確認

- 統括ノードの停止状態が `active` 接続と `synchronizing` 候補へ伝わる。
- 停止通知時に実行ノードがその使用者の管理下プロセス停止を要求する。
- 停止中に実行ノードが切断して再接続しても、新規操作を受け付けない。
- 再開後も古い `stop_generation` の要求を拒否する。
- 停止中に接続できなかった実行ノードは、再接続時の状態同期前に操作可能にならない。

### 使用者停止の成功確認

統括ノードを停止状態の正とし、各遠隔要求へ検証済み主体と `stop_generation` を含める。
実行ノードは同期済み世代より古い要求を拒否する。

## 初期設定と実機確認

利用者向け手順に次を追加する。

1. 追加 PC へ同じ版の RemoteDesktopMCP と Desktop Commander を導入する。
2. 追加 PC を既存 tailnet へ参加させる。
3. 実行ノードで `init --role executor` を実行し、接続先未設定のまま固定 `node_id` と表示名を生成する。
4. 統括ノードで対象 `node_id` を `add-executor` へ渡し、専用事前共有鍵を生成して登録する。
5. 実行ノードで `set-coordinator --psk-stdin` を実行し、統括ノードの接続先、ポート、同じ事前共有鍵を1回の設定更新で保存する。
6. 統括ノード、実行ノードの順に起動する。
7. `node_list` で接続状態とファイルルートを確認する。
8. `node_id` を指定してファイル操作、プロセス操作、転送を確認する。
9. 事前共有鍵更新と登録解除を確認する。

実機確認は統括ノード1台、実行ノード2台以上で実施する。
1台を切断した状態、再接続後、実行ノード再起動後も確認する。

## 通常確認

実装担当とは別セッションで、複数 PC 実行ノード追加・登録の要件、設計、全差分、直接依存、試験、現在 HEAD の自動検証記録を確認する。
指摘修正は実装工程へ戻し、同じ指摘識別子で解消確認する。

## 独立最終確認

通常確認と実装を担当していない別セッションで、実装の最終 HEAD を固定して確認する。
最終報告専用の `git commit` を使う場合は、製品、設計、自動検証定義、設定の変更を同じ履歴単位へ混ぜない。
統合操作は利用者が行う。

## 最終完了条件

- 複数 PC 実行ノード追加・登録の完了条件をすべて満たす。
- 利用者向け PC 追加、事前共有鍵更新、登録解除手順がある。
- ローカルの構文検査、型検査、構築確認、対象試験が成功する。
- 対象プルリクエストの現在の `HEAD SHA` と完全一致する必須自動検証記録を確認する。
- 詳細報告をリポジトリへ保存し、プルリクエストへ簡易報告を投稿する。
